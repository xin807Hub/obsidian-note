# SJWA 断电前安全停机方案

## Summary
目标不是普通“停应用”，而是提供一个断电前的一键“安全停机”入口，帮客户在页面上完成业务进程与数据库的有序停止，降低服务器断电导致 MySQL / ClickHouse 数据损坏的风险。

本次默认行为为：
- 点击页面按钮后，仅执行“安全停服务”
- 不自动执行宿主机关机
- 停机完成后，设备进入“可人工断电”状态
- 若个别组件停机失败，流程继续尽量停止其余组件，并把失败项写入日志

文档落点建议为 `docs/需求/断电前安全停机方案.md`。

## Key Changes
- 前端入口
  - 复用现有 `vue/web/src/view/systemTools/system/system.vue` 页面，不新增菜单。
  - 将现有“重启服务（开发中）”按钮改为“安全停机”或“断电前停机”。
  - 点击后弹出强提醒确认框，文案明确说明：
    - 将停止业务服务和数据库服务
    - 页面随后可能断开
    - 完成后可人工断电
  - 接口返回成功后，前端提示“停机指令已下发，请等待 10-30 秒后断电”，并禁用重复点击。

- 后端接口
  - 新增独立控制模块，建议命名 `systemControl`，避免与现有 `/system/*` 配置接口混淆。
  - 新增接口：`POST /systemControl/safeShutdown`
  - 接口采用“先应答、后执行”模式：
    - 权限校验通过后立即返回“已受理”
    - 后台异步延迟 1 到 2 秒开始执行停机流程
    - 这样可以保证 HTTP 响应先发出，再停止 `nta_server`

- 停机流程编排
  - 目标原则：先停业务，再停数据库，最后停当前 Web/API 服务。
  - 建议顺序：
    1. 停止守护拉起单元：`start_nta_server`
    2. 停止业务处理单元：`data_timer`、`go_etl`、`fsrs`
    3. 停止主业务服务：`nta_server`
    4. 停止 MySQL
    5. 停止 ClickHouse
  - 之所以先停守护，是为了避免 `start_nta_server` 把已停止的业务再拉起。
  - 之所以数据库放后面，是为了先切断应用层新请求、新写入和聚合任务，再关闭存储层。

- 数据库停止策略
  - MySQL
    - 需要兼容当前仓库里的 Docker 部署方式，优先识别 `mysql8` 容器。
    - 若容器存在且运行，则使用容器停止方式安全停止。
    - 若未来存在 systemd 管理的 MySQL，再补充 `systemctl stop mysqld/mysql` 分支。
  - ClickHouse
    - 需要兼容两类环境：
      - systemd 管理的 `clickhouse-server`
      - Docker 容器管理的 `clickhouse`
    - 优先检测 systemd unit 是否存在；存在则 `systemctl stop clickhouse-server`
    - 否则检测 ClickHouse 容器并执行容器停止
  - 两类数据库都按“存在则停，不存在跳过”处理，避免不同现场环境下接口直接失败。

- 执行器与日志
  - 后端新增统一停机执行器，封装：
    - `systemctl stop`
    - `systemctl is-active`
    - `systemctl list-unit-files`
    - `docker ps`
    - `docker stop`
  - 每一步记录：
    - 目标组件
    - 检测到的运行方式
    - 执行结果
    - 失败原因
  - 流程采用“尽量停完并记日志”：
    - 某一步失败不阻断后续组件停机
    - 最终汇总写入日志，供运维核查

- 权限与安全
  - 接口只挂私有路由，仅允许管理员角色调用。
  - 增加操作审计日志，记录操作者、时间、来源 IP、停机结果摘要。
  - 按钮默认只对高权限用户显示，避免误操作。

## Public APIs / Interfaces
- 前端新增 API
  - `safeShutdown()`
- 后端新增接口
  - `POST /systemControl/safeShutdown`
- 返回格式保持项目统一结构
  - 建议返回：`code=0`，`msg=停机指令已受理`
  - `data` 可带 `accepted: true`
- 本次不要求新增数据库表
- 本次不强制新增配置文件项
  - 服务名与容器名先按仓库和现场约定内置
  - 如后续客户现场差异大，再扩展为 `service.yaml` 可配置名单

## Test Plan
- 后端单测
  - systemd 单元存在/不存在时的分支覆盖
  - Docker 容器存在/不存在时的分支覆盖
  - 单步失败后仍继续执行后续停机
  - 顺序校验：`start_nta_server` 必须先于业务服务停止，数据库必须晚于业务停止
  - `nta_server` 必须最后一批停止，确保接口响应先返回

- 联调场景
  - 仅业务服务存在时，能完成业务停机
  - MySQL 为 Docker、ClickHouse 为 systemd 的混合环境可完成停机
  - ClickHouse 为 Docker 环境时也可完成停机
  - 某个组件不存在时整体流程不报致命错误
  - 某个组件 stop 失败时其余组件仍继续停机
  - 前端在收到成功响应后，后续页面断开属于预期行为

- 人工验收
  - 点击按钮后 10 到 30 秒内，业务服务与数据库均停止
  - 运维侧可通过 `systemctl status` / `docker ps` 确认组件已停
  - 停机后人工断电，不再依赖先登录服务器逐个执行停库命令

## Assumptions
- “安全停机”本次定义为“断电前安全停服务”，不自动执行宿主机关机。
- 目标是帮助客户简化断电前操作，不是做完整的运维编排平台。
- 当前现场可能存在 systemd 与 Docker 混合部署，因此方案采用“运行方式自适应检测”。
- 失败策略按“尽量停完并记日志”执行，不做遇错即停。
- 先不做停机完成状态查询页；第一版只做按钮下发与后台异步执行。
- 页面入口继续放在现有系统工具页，不新增独立页面。
