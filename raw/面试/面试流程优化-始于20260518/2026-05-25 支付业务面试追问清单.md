# 支付业务面试追问清单（2026-05-25）

本文用于复习支付类业务的面试追问方式，尤其适用于候选人简历中出现以下关键词时：

- 支付申请
- 银行接口
- 招行 CBS
- 转账审批
- 付款参数校验
- 重复支付
- 支付状态同步
- 支付规则配置化

这类项目的重点不是考候选人是否懂金融业务名词，而是看他是否具备后端工程闭环能力：

- 是否理解外部系统调用的不确定性
- 是否理解幂等、状态机、补偿、对账
- 是否能把规则配置化讲清楚
- 是否有异常处理和线上问题意识

---

## 一、面试官先抓主线

如果候选人说自己做过支付、转账、CBS、银行接口，不要马上问散题。先让他讲完整链路。

建议开场问题：

> 你负责的这块支付业务，从用户提交付款申请，到银行侧最终审批成功，中间完整链路讲一遍。

重点听他是否能讲清：

1. 前端提交了什么信息。
2. 后端做了哪些参数校验。
3. 本地生成了什么业务单号或请求流水号。
4. 调用银行接口前，本地状态是什么。
5. 银行接口返回后，本地状态怎么变。
6. 银行审批结果怎么同步回来。
7. 失败、超时、重复提交怎么处理。

如果候选人只说“我们调了银行接口，然后成功就更新状态”，说明还没有进入工程细节。

## 二、核心追问 1：重复支付和幂等

### 可以这样问

> 用户在前端连续点了两次付款，或者网络抖动导致前端重试了两次，你们怎么防止重复支付？

### 继续追问

- 幂等号是谁生成的，前端还是后端？
- 业务单号和请求流水号有什么区别？
- 数据库层有没有唯一索引兜底？
- 第二次请求进来时，是直接拒绝，还是返回第一次处理结果？
- 如果第一次请求超时了，第二次请求应该怎么处理？

### 好答案要点

支付类接口不能只靠前端按钮置灰。后端必须做幂等控制。

比较完整的设计是：

1. 后端为每一笔支付申请生成唯一业务单号。
2. 调用外部银行接口时生成请求流水号或使用业务单号作为幂等键。
3. 数据库对业务单号或幂等号建立唯一索引。
4. 请求进来后先查本地支付状态。
5. 如果已经成功或处理中，不能再次发起真实支付。
6. 重复请求应返回原有处理结果，或者返回“处理中”，而不是重新扣款。

关键词：

- 幂等号
- 业务单号
- 请求流水号
- 唯一索引
- 状态判断
- 重复请求返回原结果

### 扣分信号

- 只说“前端防重复点击”
- 只说“加锁”，但说不清锁的范围和失效后果
- 只说“用事务”，没有说明外部接口不受本地事务控制
- 调用超时后直接判失败

## 三、核心追问 2：支付状态机

### 可以这样问

> 一笔支付申请从创建到最终结束，你们一般会有哪些状态？

### 继续追问

- 调银行接口之前是什么状态？
- 调银行接口超时是什么状态？
- 银行已受理但还没审批完成是什么状态？
- 哪些状态是终态？
- 状态更新有没有顺序限制？
- 能不能从成功改回审批中？

### 好答案要点

支付业务不能只用“成功、失败”两个状态。因为外部银行系统通常是异步审批，接口返回成功只代表申请提交成功，不代表最终付款成功。

可以设计类似状态：

| 状态 | 含义 |
| --- | --- |
| 待提交 | 本地申请已创建，还没调用银行 |
| 提交中 | 正在调用银行接口 |
| 已提交 | 银行已受理申请 |
| 审批中 | 银行侧审批流程未结束 |
| 成功 | 银行确认付款成功 |
| 失败 | 银行明确返回失败 |
| 未知 | 调用超时或返回不明确，需要补偿查询 |
| 已撤销 | 申请被人工或流程撤销 |

状态更新要有约束：

- 中间态可以流转到终态。
- 终态不能随便改回中间态。
- 超时不能直接当失败。
- 每次状态变更最好记录日志或流水。

关键词：

- 状态机
- 终态
- 中间态
- 未知状态
- 状态流转约束
- 状态变更日志

### 扣分信号

- 只说“成功和失败”
- 把“接口提交成功”等同于“付款成功”
- 不知道超时状态怎么处理
- 没有状态变更记录意识

## 四、核心追问 3：外部接口超时

### 可以这样问

> 你调用银行付款接口时，接口超时了。本地应该记录成功、失败，还是别的状态？

### 继续追问

- 如果银行其实已经受理成功了，但你本地超时了怎么办？
- 如果你再发起一次，会不会重复付款？
- 你怎么知道银行侧最终状态？
- 这个状态谁来修正？

### 好答案要点

外部接口超时不能简单判失败。因为请求可能已经到达银行，银行可能已经受理，只是响应没有回到本系统。

合理处理方式：

1. 本地记录为 `未知` 或 `待确认`。
2. 保存请求流水号、请求参数摘要、调用时间、超时原因。
3. 不允许用户直接再次发起真实支付。
4. 通过定时任务按流水号查询银行侧状态。
5. 查询到明确结果后，再更新本地状态。
6. 多次查询仍无结果时，进入人工处理队列。

关键词：

- 未知状态
- 待确认
- 补偿查询
- 请求流水号
- 人工处理
- 防止重复发起

### 扣分信号

- 超时直接改失败
- 超时后让用户重新点一次付款
- 没有流水号意识
- 没有补偿查询机制

---

## 五、核心追问 4：支付申请和审批状态一致性

### 可以这样问

> 本地支付申请状态和银行审批状态，怎么保证一致？

### 继续追问

- 只靠数据库事务够不够？
- 如果本地提交成功，但查询银行失败怎么办？
- 如果银行状态已经成功，本地还是审批中怎么办？
- 有没有定时补偿或对账？
- 状态更新怎么保证幂等？

### 好答案要点

如果只是本系统内部两张表，例如申请表和日志表，本地事务可以保证一致。

但银行 CBS 是外部系统，外部系统不受本地数据库事务控制，所以只说“用事务”是不完整的。

完整答案应该是：

1. 本地操作使用数据库事务，保证申请表、流水表、日志表一致。
2. 调外部银行接口前后，明确本地状态。
3. 外部接口返回不明确时，进入未知状态。
4. 使用银行流水号或业务单号做补偿查询。
5. 定时任务同步审批状态。
6. 状态更新要幂等，不能重复推进或倒退。
7. 必要时做对账，发现本地和银行侧状态不一致时进入差异处理。

关键词：

- 本地事务
- 外部系统不受本地事务控制
- 状态机
- 幂等更新
- 补偿查询
- 对账
- 差异处理

### 扣分信号

- 只说“事务”
- 不理解外部接口无法纳入本地事务
- 没有定时补偿意识
- 没有对账意识

## 六、核心追问 5：规则配置化

### 可以这样问

> 你刚才说不同银行、不同账户类型需要的付款参数不一样。一开始写死在代码里，后面改成数据库配置。这个配置表大概怎么设计？

### 继续追问

- 配置表有哪些字段？
- 一条规则如何表达“某字段必填”？
- 规则怎么生效，是立即生效还是定时刷新？
- 规则配错了怎么办？
- 能不能回滚到上一个版本？
- 一条规则校验失败，怎么告诉用户具体哪个字段错了？

### 好答案要点

规则配置化不是简单把字段放数据库，而是要让规则具备可维护、可解释、可回滚能力。

配置表可以包含：

| 字段 | 含义 |
| --- | --- |
| bank_code | 银行编码 |
| pay_type | 付款类型 |
| account_type | 账户类型 |
| field_name | 被校验字段 |
| condition_expr | 规则触发条件 |
| required_flag | 是否必填 |
| value_rule | 值范围或格式 |
| error_code | 错误码 |
| error_message | 错误提示 |
| suggestion | 处理建议 |
| enabled | 是否启用 |
| version | 规则版本 |
| updated_by | 修改人 |
| updated_at | 修改时间 |

关键词：

- 条件表达式
- 字段必填
- 值域校验
- 错误码
- 版本号
- 启停
- 审计
- 回滚

### 扣分信号

- 只说“放数据库”
- 不知道规则怎么生效
- 不考虑规则配错后的回滚
- 失败后只能返回“参数错误”

## 七、核心追问 6：规则命中后如何返回具体错误

### 可以这样问

> 如果某条付款规则校验失败，比如招行对公转账必须填写“是否加急”，你怎么把具体错误返回给前端或用户？

### 继续追问

- 错误信息写在代码里还是配置里？
- 前端怎么知道是哪个字段错了？
- 如果一次有多个字段错误，是返回一个还是返回列表？
- 错误码有什么用？
- 错误信息是否需要给业务人员维护？

### 好答案要点

规则配置化以后，错误解释也应该配置化。否则规则虽然从代码挪到了数据库，但失败原因仍然写死在代码里，维护成本没有真正降下来。

规则表里应该保存：

- 字段名
- 错误码
- 错误提示
- 处理建议

单个错误可以返回：

```json
{
  "success": false,
  "code": "PAY_PARAM_001",
  "message": "招行对公转账必须填写是否加急",
  "field": "isUrgent",
  "suggestion": "请补充是否加急字段后重新提交"
}
```

多个错误可以返回：

```json
{
  "success": false,
  "code": "PAY_PARAM_INVALID",
  "message": "付款参数校验失败",
  "errors": [
    {
      "field": "isUrgent",
      "code": "PAY_PARAM_001",
      "message": "招行对公转账必须填写是否加急"
    },
    {
      "field": "remark",
      "code": "PAY_PARAM_002",
      "message": "转账备注不能超过 50 个字符"
    }
  ]
}
```

关键词：

- 结构化错误
- 字段名
- 错误码
- 错误列表
- 处理建议
- 规则和错误提示一起配置

### 扣分信号

- 只返回“参数错误”
- 不知道哪个字段错了
- 错误提示全写死在代码里
- 没有错误码意识

## 八、核心追问 7：缓存刷新失败

### 可以这样问

> 规则配置放到数据库后，你用本地缓存提高性能。如果缓存刷新失败怎么办？

### 继续追问

- 刷新失败后还能不能继续用旧规则？
- 如果数据库里规则已经改了，但缓存还是旧的，会有什么风险？
- 是否需要告警？
- 是否需要手动刷新入口？
- 如果规则变更很关键，如何保证生效？

### 好答案要点

缓存刷新失败不能简单说“重试”。要区分旧缓存是否仍然可用。

比较稳的方式：

1. 缓存刷新失败时，继续使用上一版可用规则。
2. 记录刷新失败日志。
3. 触发告警，通知维护人员。
4. 下一轮继续重试。
5. 对关键规则变更，可以提供手动刷新或发布确认机制。
6. 缓存中保存规则版本，便于排查当前服务使用的是哪一版规则。

关键词：

- 旧规则兜底
- 刷新失败告警
- 重试
- 手动刷新
- 规则版本
- 可观测性

### 扣分信号

- 刷新失败后缓存直接清空
- 没有告警
- 不知道当前服务使用哪一版规则
- 只说“人工排查”，没有自动发现机制

---

## 九、核心追问 8：规则变更灰度

### 可以这样问

> 如果银行付款规则调整了，你们怎么让新规则安全生效？有没有灰度或回滚？

### 继续追问

- 新规则是直接全量生效吗？
- 能不能只对某个银行、某类账户、某个租户生效？
- 配错规则后怎么快速回滚？
- 规则变更是否需要审批？
- 有没有记录谁改了什么？

### 好答案要点

0-3 年候选人未必实际做过灰度，但优秀候选人至少能推演。

可以从简单到复杂回答：

1. 规则有启停开关。
2. 规则有版本号。
3. 规则变更有操作日志。
4. 关键规则变更需要审批。
5. 支持按银行、账户类型、租户或机构范围生效。
6. 新规则出问题时，可以回滚到上一版。

关键词：

- 启停开关
- 版本号
- 生效范围
- 审批
- 审计日志
- 回滚

### 扣分信号

- 直接改数据库，全量立即生效
- 配错只能重新改回来
- 没有版本和操作记录
- 不知道规则变更会影响线上支付

## 十、核心追问 9：支付对账

### 可以这样问

> 如果本地系统显示付款成功，但银行侧实际失败，或者银行侧成功但本地还是审批中，你们怎么发现并处理？

### 继续追问

- 有没有银行对账文件？
- 没有对账文件时怎么做？
- 差异数据怎么记录？
- 谁来处理差异？
- 修正状态时怎么留痕？

### 好答案要点

支付系统最终要面对“本地状态和银行状态不一致”的问题。仅靠接口实时返回不够。

常见方式：

1. 银行提供对账文件时，定时下载并解析。
2. 没有对账文件时，按业务单号或银行流水批量查询。
3. 本地生成差异表。
4. 差异进入人工复核流程。
5. 状态修正必须记录操作人、原因、前后状态。
6. 对账结果要能追溯。

关键词：

- 对账文件
- 批量查询
- 差异表
- 人工复核
- 状态修正
- 操作留痕

### 扣分信号

- 完全没听过对账
- 认为银行接口返回成功就永远没问题
- 人工改库但不留痕

## 十一、30 分钟面试脚本

如果候选人有支付类项目，可以用这套 30 分钟脚本。

### 1. 自我介绍和项目选择，3 分钟

> 你先简单介绍一下自己，然后挑一个你最熟的支付或转账相关模块展开。

### 2. 核心链路，7 分钟

> 从用户提交付款申请，到银行侧最终审批成功，中间完整链路讲一遍。

追问：

- 主要表有哪些？
- 本地状态怎么流转？
- 外部接口返回什么？
- 你亲手负责哪一段？

### 3. 幂等和重复支付，5 分钟

> 用户点两次付款，或者接口超时后前端重试，怎么防止重复支付？

追问：

- 幂等号怎么设计？
- 数据库怎么兜底？
- 第二次请求返回什么？

### 4. 外部接口超时和状态一致性，7 分钟

> 调银行接口超时了，本地状态怎么记？后面怎么确认最终结果？

追问：

- 能不能直接判失败？
- 怎么补偿查询？
- 状态能不能回退？
- 本地和银行不一致怎么办？

### 5. 规则配置化，5 分钟

> 不同银行需要不同付款参数，你们怎么做参数规则配置化？

追问：

- 配置表怎么设计？
- 规则失败怎么返回具体错误？
- 缓存刷新失败怎么办？
- 规则配错怎么回滚？

### 6. 总结判断，3 分钟

最后快速判断：

- 他是亲手做过，还是只知道业务流程？
- 他能不能讲出异常场景？
- 他有没有状态机、幂等、补偿意识？
- 他是否能从 Java 项目迁移到 Go 服务？

## 十二、评分表

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| 项目真实性 | 只会讲业务名词 | 能讲部分接口和表 | 能讲完整链路和自己负责内容 |
| 幂等意识 | 只靠前端防重复 | 知道唯一号或锁 | 能讲清幂等号、状态判断、唯一索引 |
| 状态机意识 | 只有成功失败 | 有处理中、失败等状态 | 能区分中间态、终态、未知态 |
| 外部接口异常 | 超时直接失败 | 知道重试 | 知道未知状态、补偿查询、人工处理 |
| 规则配置化 | 只说放数据库 | 能说出部分字段 | 能说出版本、启停、错误码、回滚、审计 |
| 线上闭环 | 没有日志排查意识 | 能说日志和重试 | 能说告警、补偿、对账、留痕 |

建议判断：

- `24-30 分`：支付类项目理解较扎实，值得推进。
- `18-23 分`：有业务经验，但工程闭环一般，可结合岗位紧急程度判断。
- `12-17 分`：只做过局部功能，谨慎推进。
- `12 分以下`：不建议推进。

## 十三、强弱信号速查

### 强信号

- 主动提到幂等号、业务单号、请求流水号。
- 能区分“银行受理成功”和“付款最终成功”。
- 知道外部接口超时不能直接判失败。
- 能讲出状态机和终态保护。
- 能讲出补偿查询或对账。
- 规则配置化能讲到错误码、版本、启停、回滚。
- 知道人工处理也要留痕。

### 弱信号

- 只说“用事务保证一致”。
- 只说“前端防重复点击”。
- 只说“失败就重试”。
- 不知道调银行超时后本地怎么记状态。
- 把接口提交成功当作付款成功。
- 规则配置化只停留在“放数据库”。
- 错误返回只有“参数错误”。

## 十四、面试官记忆版

支付类项目就抓 6 个词：

```text
链路、幂等、状态、超时、补偿、对账
```

规则配置化就抓 6 个词：

```text
条件、字段、错误、版本、启停、回滚
```

如果候选人能围绕这 12 个词讲清楚，说明他不是只做了简单 CRUD。

如果候选人只能说“调用接口、保存结果、失败重试、用事务”，说明他的支付项目经验还停留在表层。
