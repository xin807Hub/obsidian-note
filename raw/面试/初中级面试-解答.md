# 初中级程序员面试题参考解答

## 数据库与数据访问

### 1. 员工打卡记录表里，怎么找出连续三天都有打卡的员工？

#### 参考答案要点

- 先把打卡时间按天归一，避免同一天多次打卡影响结果：`date(check_time)`。
- 典型做法是先按员工、日期去重，再用窗口函数 `row_number()` 构造连续分组。
- 核心思路：`打卡日期 - row_number()` 相同的记录属于同一段连续日期。
- 再按员工和连续分组聚合，筛出连续天数大于等于 3 的员工。

```sql
WITH base AS (
  SELECT DISTINCT emp_name, DATE(check_time) AS d
  FROM attendance
), grp AS (
  SELECT emp_name,
         d,
         DATE_SUB(d, INTERVAL ROW_NUMBER() OVER (PARTITION BY emp_name ORDER BY d) DAY) AS g
  FROM base
)
SELECT emp_name
FROM grp
GROUP BY emp_name, g
HAVING COUNT(*) >= 3;
```

- 如果面试官追问“没有窗口函数怎么办”，也可以用自连接或变量，但可读性和稳定性通常不如窗口函数。

### 2. 怎么判断两个 IP 段是否交叉重叠？

#### 参考答案要点（含 IPv4 / IPv6）

1. **先统一模型**
   - 把 IP 段都转成闭区间 `[start, end]`。
   - 同时记录 `ip_version`，`IPv4` 和 `IPv6` 不混比。

2. **核心判定公式**
   - 两个区间 `A=[aStart, aEnd]`、`B=[bStart, bEnd]` 交叉当且仅当：
   - `aStart <= bEnd && bStart <= aEnd`
   - 等价写法：`!(aEnd < bStart || bEnd < aStart)`

3. **IPv4 / IPv6 数值化**
   - `IPv4` 转无符号 32 位整数。
   - `IPv6` 转无符号 128 位，或统一转 16 字节大端序。
   - 不要直接按字符串比较大小。

4. **MySQL 字段类型怎么选**
   - 只存 `IPv4`：可用 `INT UNSIGNED`。
   - 同时支持 `IPv4 / IPv6`：推荐 `BINARY(16)`，再加 `ip_version TINYINT` 区分版本。
   - 如果是 IP 段，就存 `start_ip`、`end_ip` 两个字段。
   - 不建议主存储直接用 `VARCHAR(45)` 做范围比较和索引。
   - 前端展示时，建议后端把二进制或数值 IP 转成字符串返回；除非有导出、人工排查诉求，一般不建议再冗余一份 `VARCHAR` 展示字段。

5. **入参校验**
   - `start <= end`，否则是非法区间。
   - 支持 CIDR 时，先把 `192.168.1.0/24` 这类写法转成 `[start, end]`。

6. **数据库判重 SQL**

```sql
SELECT id
FROM ip_range
WHERE ip_version = :ipVersion
  AND start_num <= :inputEnd
  AND end_num >= :inputStart
LIMIT 1;
```

- 索引建议：`(ip_version, start_num, end_num)`。
- 如果 `IPv6` 用 `BINARY(16)` 按大端序存，也可以按同样逻辑比较。

### 3. 如何查出“曾命中高危但最终已恢复”的会话？

#### 参考答案要点

- 关键词是“曾命中高危”和“最终已恢复”，说明要看同一会话的状态流转，而不是只看某一条记录。
- 常见做法是先按会话聚合出“是否出现过高危”和“最后状态是什么”。
- 如果有事件时间字段，可用窗口函数先取每个会话最新一条，再和历史高危记录关联。

```sql
WITH latest AS (
  SELECT session_id, status,
         ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY event_time DESC) AS rn
  FROM session_event
), risk AS (
  SELECT DISTINCT session_id
  FROM session_event
  WHERE risk_level = 'HIGH'
)
SELECT l.session_id
FROM latest l
JOIN risk r ON l.session_id = r.session_id
WHERE l.rn = 1
  AND l.status = 'RECOVERED';
```

- 面试里要主动说清：最终状态判断必须基于时间排序，不能直接 `MAX(status)` 这种错误写法。

### 4. MySQL 全字段加索引会更快吗？

#### 参考答案要点

- 不会。索引不是越多越快，读写收益和维护成本要一起看。
- 写入、更新、删除时，每个索引都要维护，索引越多写放大越严重。
- 索引也占磁盘和内存，可能让缓冲池命中率下降。
- 查询优化器还可能因为候选索引太多而选错计划。
- 正确做法是围绕高频查询、过滤条件、排序条件、覆盖查询来设计索引。

### 5. MySQL 里，单列索引和联合索引怎么选？

#### 参考答案要点

- 不是“哪个更高级”，而是看查询条件是不是经常一起出现。
- 如果 SQL 常按 `a`、`b` 组合过滤或排序，联合索引通常比给 `a`、`b` 各建一个单列索引更有效。
- 联合索引要注意最左前缀原则，比如 `(a, b, c)` 更容易命中 `a`、`a+b`、`a+b+c`，不一定能高效命中单独的 `b`、`c`。
- 单列索引适合条件相对独立、复用面广的字段；联合索引适合稳定的高频组合查询。
- 索引设计要围绕真实 SQL、过滤条件、排序条件和回表成本，不要只按字段个数机械建索引。

### 6. MySQL 里，如果 `select *` 查一张一千万行的大表，内存会飙升吗？

#### 参考答案要点

- 不能简单回答“一定会”或“一定不会”，要分数据库端和应用端看。
- MySQL 服务端未必一次把所有结果全塞进内存，但应用如果一次性把结果集全部加载进来，堆内存很容易飙升。
- 风险不只是内存，还包括网络传输、回表、锁持有时间、应用处理耗时。
- 真正的生产建议是分页、流式读取、只查需要字段、限制导出规模。

#### 追问建议（如果面试者只回答"会的"）

> **目标**：区分"背过概念"和"真正理解两端行为"。

1. **先问端**
   "你说的内存飙升，是指 MySQL 服务端，还是应用服务端？"
   → 预期他能说明两端是独立的：MySQL 服务端可以边扫描边发，**不一定**全缓冲在内存；而应用端如果 ORM 一次性把结果集全量塞到 List 里，堆内存才会飙升。

2. **再问服务端机制**
   "MySQL 执行这条语句时，服务端会不会先把一千万行全部缓冲在内存里再发给客户端？"
   → 预期提到 Innodb 可以流式发送，但如果涉及排序、分组、临时表，仍可能需要内部缓冲或落盘。

3. **追问应用端/ORM 行为**
   "那我用 MyBatis 直接返回一个 List，这一千万行对象存在哪里？"
   → 预期说明 JDBC 默认可能一次性拉取，`ResultSet` 被框架映射成一千万个对象后堆内存会直接吃满。

4. **工程解法**
   "生产里真要导一千万行，你怎么做让内存可控？"
   → 预期提到流式/游标读取、分页（注意深分页问题）、只查必要字段、异步任务拆分。

5. **加分追问**
   "如果这条 SQL 还开了一个大事务去执行，除了内存还会带来什么风险？"
   → 预期提到长事务持有锁、undo log 膨胀、阻塞其他 DML，能说到这一步说明真有线上经验。

### 7. MyBatis 中 `#{}` 和 `${}` 有什么区别？什么时候该用哪个？

#### 参考答案要点

- `#{}` 是预编译参数，占位后由驱动安全绑定，能防 SQL 注入。
- `${}` 是字符串直接拼接，适合表名、排序字段这类不能参数化的位置，但有注入风险。
- 值条件一律优先用 `#{}`。
- 如果不得不用 `${}`，要做白名单校验，例如排序字段只能从固定枚举里选。

### 8. MyBatis 的一级缓存和二级缓存有什么区别？使用时要注意什么？

#### 参考答案要点

- 一级缓存默认开启，作用域是同一个 `SqlSession`。
- 二级缓存是 Mapper 级别，需要显式开启，并且要考虑数据一致性。
- 一级缓存命中条件比较苛刻：同一会话、相同 SQL、相同参数、期间没有执行更新。
- 二级缓存适合读多写少、更新路径明确的场景；高频变更数据一般不建议强依赖。
- 面试里要讲到缓存失效和脏读风险，否则答案不完整。

### 9. MyBatis 分页时为什么容易出现 N+1 问题？怎么解决？

#### 参考答案要点

- 分页本身不难，难点在于关联对象装配时容易出现 N+1。
- N+1 本质是先查一页主数据，再按每条记录补查子数据，导致 SQL 数量爆炸。
- 解决思路通常有三类：`JOIN` 一次查、批量 `IN` 回填、明确按需加载。
- 如果用了分页插件，要确认分页发生在真正需要分页的主查询上，而不是错误地作用在关联结果上。

### 10. MyBatis `ExecutorType.BATCH` 批量写入时，事务边界和回滚怎么设计？

#### 参考答案要点

- `BATCH` 提升的是发送效率，不会自动帮你做好事务设计。
- 事务边界要按业务语义划分，不要为了“更快”把太大批次塞进一个事务里。
- 一般要显式 `flushStatements()` 和 `commit()`，异常时统一回滚。
- 如果批量数据很大，常见做法是按批次分段提交，兼顾回滚成本和锁持有时间。
- 面试里要说明：一旦一批里部分失败，是否允许部分成功，取决于业务要求，而不是框架默认行为。

### 11. MyBatis 动态 SQL（`<if>/<where>/<trim>/<foreach>`）出现空条件或语义错误，怎么排查？

#### 参考答案要点

- 先打印最终生成的 SQL 和绑定参数，而不是只盯 XML。
- 常见问题有：条件为空导致全表查、`AND/OR` 残留、`IN ()` 空集合、参数名不匹配。
- `<where>`、`<trim>` 就是为了解决多余前缀和分隔符问题，能用就别手写拼接。
- 对更新和删除语句，要加防御性校验，避免空条件直接落到线上。

### 12. MyBatis-Plus 条件构造器误用导致全表更新/删除，如何防护？

#### 参考答案要点

- 风险点通常不是框架，而是业务代码在条件为空时仍然执行了 `update` 或 `remove`。
- 防护手段：业务层判空、开启 SQL 拦截器、防全表更新插件、关键操作加审批或开关。
- 对动态条件对象，要区分“用户没传”和“传了空值”两种语义。
- 面试里可以补一句：删除或更新前先打印影响条件和 SQL，是非常实际的防线。

### 13. MyBatis TypeHandler 处理 JSON/枚举映射异常时，如何定位根因？

#### 参考答案要点

- 先确认异常发生在入库、出库，还是中间结果映射阶段。
- 检查数据库字段类型、Java 字段类型、TypeHandler 注册位置是否一致。
- JSON 类型问题常见于序列化器不一致、字段格式不合法、空值处理不统一。
- 枚举问题常见于数据库里存的是 code，但代码按 name 解析，或者新增枚举值未同步。
- 排查顺序通常是：SQL 原始值 -> JDBC 读取值 -> TypeHandler -> 实体字段。

### 14. MyBatis 插件链（如分页拦截器）顺序不当，为什么会引发 SQL 异常或性能劣化？

#### 参考答案要点

- MyBatis 插件本质是责任链，顺序不同，改写 SQL 的结果就可能不同。
- 如果分页、租户、数据权限、多表改写这类插件顺序不对，可能出现 SQL 语义错误或重复包裹。
- 分页插件如果在错误阶段执行，可能对已经被改写的 SQL 再次加工，导致性能明显变差。
- 排查时要看最终 SQL，而不是只看单个插件的“理论行为”。

## Java 基础与并发

### 15. 用 `foreach` 遍历集合时直接调用 `remove()` 会报错吗？

#### 参考答案要点

1. **不一定，但绝大多数情况会报错**
   - 通常下一轮到 `iterator.next()` 时，`expectedModCount != modCount`，立刻抛 `ConcurrentModificationException`。
   - **有一个“刚好不报错”的陷阱场景**：如果删除的是倒数第二个元素，当前循环正常结束，但由于内部游标已等于集合大小，迭代器直接判定 `hasNext() == false`，并不会再调用 `next()` 去做 fail-fast 检查，结果“静默成功”但漏掉了最后一个元素。

2. **底层原因与 fail-fast**
   - `foreach` 底层也是迭代器遍历；迭代器维护了 `expectedModCount`，而集合的 `remove()` 会修改 `modCount`。
   - 两者不一致时触发 `ConcurrentModificationException`，这是集合的 fail-fast 机制。
   - fail-fast 是“尽早失败”，属于尽力检测，**不是线程安全保证**，也不保证 100% 每次都抛出异常。

3. **正确做法**
   - 用迭代器自己的 `remove()`。
   - 用 `removeIf()`（Java 8+）。
   - 先收集要删的元素，遍历结束后统一删除。

### 16. String 处理有哪些常见的性能陷阱？

#### 场景一：`substring` 的内存风险

- Java 6 时代，`substring` 可能共享原字符串底层 `char[]`，小字符串引用会把大数组一起挂住。
- Java 7u6 之后改成复制子串内容，规避了这类内存滞留问题。
- 所以旧版本里，截一小段但长时间持有，可能让大字符串迟迟不能释放。

#### 场景二：敏感词过滤的数据结构选择

- 如果敏感词库很大，不适合反复 `String.replace` 全量扫描。
- 更常见的选择是 Trie 树或 AC 自动机。
- AC 自动机适合多模式匹配，整体效率更稳定。
- `StringBuilder` 适合结果拼装，但不解决“大量词条匹配”的根问题。

### 17. 为什么有人说 Java 泛型是"伪泛型"？

#### 参考答案要点

- 因为 Java 泛型在编译后会做类型擦除，运行期通常拿不到真实泛型参数。
- `List<String>` 和 `List<Integer>` 运行期大多是同一个原始类型。
- 这也是为什么不能直接 `new T()`、不能创建 `new List<String>[10]`。
- 编译器会补充强转和桥接方法，保证源码层面的类型安全体验。

### 18. 线程池里的任务越堆越多，你怎么判断问题出在哪？

#### 参考答案要点

- 先区分是“生产太快”还是“消费太慢”。
- 关键观察项：活跃线程数、队列长度、任务平均耗时、拒绝次数、下游 RT、错误率。
- 如果线程都在忙，通常是任务执行慢；如果线程没满但队列长，可能是配置不合理。
- 进一步要看任务是 CPU 密集、IO 阻塞，还是被外部系统卡住。
- 线程池问题很多时候不是线程池本身，而是下游依赖、锁竞争、数据库慢查询导致的连锁反应。

### 19. HashMap 的扩容机制是怎样的？

#### 参考答案要点

- 底层数组长度通常是 2 的幂。
- 当元素数量超过 `capacity * loadFactor` 时触发扩容，默认负载因子一般是 `0.75`。
- 扩容通常是容量翻倍，然后把旧元素重新分布到新数组里。
- Java 8 里，节点迁移要么留在原索引，要么移动到 `原索引 + oldCap`，比早期版本更高效。

### 20. 为什么 HashMap 扩容慢？

#### 参考答案要点

- 慢点不在平时 `put`，而在触发扩容时的集中搬迁成本。
- 扩容要申请更大数组，还要重分布原有节点。
- 如果桶里链表或红黑树元素多，迁移成本会更明显。
- 所以业务如果能预估规模，初始化给合理容量通常更稳。

### 21. 为什么 HashMap 在 Java 7 会出现死循环，而 Java 8 不会？

#### 参考答案要点

- 问题核心是并发扩容，而 `HashMap` 本身又不是线程安全的。
- Java 7 迁移链表时如果多个线程同时 `resize`，链表指针可能被改乱并形成环。
- 一旦成环，后续遍历就可能死循环，CPU 飙高。
- Java 8 调整了迁移实现，降低了成环风险，但不等于并发场景就能安全使用 `HashMap`。
- 正确结论是：并发场景应使用 `ConcurrentHashMap`。

### 22. HashMap 和 Hashtable 的区别是什么？

#### 参考答案要点

- `HashMap` 线程不安全，`Hashtable` 线程安全，但它通常是整表级同步，性能较差。
- `HashMap` 允许 `null` 键和 `null` 值，`Hashtable` 不允许。
- 现代项目里，并发安全通常优先选 `ConcurrentHashMap`，很少新用 `Hashtable`。

## 后端场景与中间件

### 23. 如果在一个页面中多次且非常快速的点击保存按钮，如何保证表单只被保存一次？

#### 参考答案要点

- 前端可以先做降噪：点击后按钮置灰、显示 `loading`、避免重复触发。
- 但真正兜底要靠后端幂等：定义稳定的 `Idempotency-Key`，同一业务动作重试时复用。
- 数据库层要有唯一约束，避免并发下“先查后插”失效。
- 常见落地流程：先写幂等记录为 `processing`，首个请求执行业务，成功后写入 `success + 响应快照`，重复请求直接返回快照。
- 面试收尾可以总结：前端防连点只能减压，后端幂等键加唯一约束才是确定性保障。

### 24. 长连接和长轮询有什么区别？各适用于什么场景？

#### 参考答案要点

- 长连接是一次建立连接后长期复用，例如 TCP 长连接、WebSocket。
- 长轮询是客户端发请求后，服务端先挂住，直到有数据或超时再返回，然后客户端再发下一次请求。
- 长连接更适合高频双向通信，长轮询更像兼容性更好的“准实时”方案。
- 长连接要关注心跳、空闲超时、连接数治理；长轮询要关注请求堆积和超时成本。

### 25. 怎么保证 MQ 消息不丢失？

#### 参考答案要点

- “不丢失”通常要分生产者、Broker、消费者三段来讲。
- 生产者侧：发送确认、重试、落库消息表或事务消息。
- Broker 侧：持久化、副本机制、刷盘策略。
- 消费者侧：手动 ACK、幂等消费、失败重试、死信队列。
- 面试里最好补一句：真正的目标通常是“可恢复、不重复或可去重”，而不是神话式的绝对零丢失。

### 26. 缓存设计要注意什么？缓存击穿、穿透、雪崩分别怎么解决？

#### 参考答案要点

- 三大常见问题是：缓存穿透、缓存击穿、缓存雪崩。
- 穿透：查不存在的数据，解决思路是布隆过滤器、空值缓存。
- 击穿：热点 Key 失效瞬间大量请求打到数据库，解决思路是互斥锁、逻辑过期、热点永不过期。
- 雪崩：大量 Key 同时失效，解决思路是过期时间打散、多级缓存、限流降级。
- 设计缓存时还要考虑一致性、预热、淘汰策略和监控。

### 27. JWT 有哪些常见的安全问题？怎么防护？

#### 参考答案要点

- JWT 适合无状态认证，但不等于“天然安全”。
- 核心风险点有：密钥泄露、过期控制不当、算法配置错误、敏感信息明文放进载荷、令牌被窃取后重放。
- 实践上要做：强密钥、短期有效期、刷新机制、只放必要信息、服务端校验签名和关键声明。
- 如果是高风险系统，还要考虑吊销、黑名单或配合服务端状态管理。

### 28. JWT 后端是怎么判断 token 正确性的？

#### 参考答案要点

- 先校验签名，确认内容没被篡改且确实是自己信任的签发方发的。
- 再校验标准声明：`exp`、`nbf`、`iat`、`iss`、`aud` 等。
- 然后结合业务校验用户状态、权限版本、是否已注销或被踢下线。
- 签名通过不等于业务一定允许通过，这是面试里很容易漏掉的一点。

### 29. JWT 是怎么防篡改的？

#### 参考答案要点

- 靠的是数字签名，不是靠 Base64 编码。
- 头和载荷会参与签名计算，服务端收到后用同样算法和密钥重新验签。
- 如果内容被改过，签名校验就过不去。
- 所以 JWT 只能防篡改，不能防“被看到”；载荷默认不是加密的。

### 30. Nacos 配置动态刷新的原理是什么？实际使用要注意什么？

#### 参考答案要点

- 核心价值是配置变更后应用无需重启即可感知新值。
- 常见前提是使用配置中心托管配置，并配合刷新机制如 `@RefreshScope`。
- 要说明两个边界：
  - 不是所有 Bean 都能无感刷新。
  - 刷新成功不等于业务一定无损，连接池、线程池这类资源型配置要看具体组件是否支持热更新。
- 线上还要关注配置变更审计、灰度发布和回滚。

## Linux 与网络编程

### 31. Linux 问题合集：怎么查看服务器上某应用的内存占用、应用端口？

#### 参考答案要点

- 看进程：`ps -ef | grep xxx`、`top -Hp <pid>`、`pidstat`。
- 看内存：`top`、`pmap -x <pid>`、`smem`，Java 进程还可结合 `jcmd/jmap`。
- 看端口：`ss -lntp`、`netstat -lntp`、`lsof -i :端口`。
- 面试时最好顺口说明你关注的是 RSS、线程数、监听端口、建立连接数，不只是“会敲命令”。

### 32. 如果是已经部署在 Linux 服务器上的应用，怎么排查现网错误？

#### 参考答案要点

- 先确认现象：报错范围、开始时间、影响接口、是否可复现。
- 再分层排查：应用日志、进程状态、CPU/内存/磁盘、网络连接、下游依赖。
- 常见顺序是：日志 -> 指标 -> 最近变更 -> 配置差异 -> 下游健康度。
- 如果是 Java 服务，还会看线程栈、GC、连接池、线程池、慢 SQL。
- 面试里强调“先止血再定位”会更像真实线上处理。

### 33. TCP 三次握手与四次挥手：连接异常怎么定位？

#### 参考答案要点

- 三次握手是为了确认双方收发能力和初始序列号同步，两次不够安全。
- 四次挥手是因为 TCP 支持半关闭，一方不发了不代表另一方也立刻不发。
- `TIME_WAIT` 常见于主动关闭方，`CLOSE_WAIT` 常见于被动关闭方没及时释放连接。
- 常用排查命令：`ss -antp`、`netstat -antp`，重点看各状态数量和趋势。
- 面试往下追时，可以自然切到“`TCP` 和 `UDP` 到底怎么选”，看候选人是否真正理解连接语义和传输模型差异。

### 34. TCP 与 UDP 选型：聊天、日志上报、实时状态该怎么选？

#### 参考答案要点

- `TCP` 是面向连接、可靠、有序、面向字节流的协议；`UDP` 是无连接、尽力而为、面向数据报的协议。
- 说 `TCP` 面向字节流，意思是它看到的是一串连续字节，不关心你业务上“发了几条消息”；发送端写两次，接收端可能一次读到，也可能分几次读到，所以应用层自己定义消息边界。
- 说 `UDP` 面向数据报，意思是发送方每发一个报文，接收方就是按一个报文一个报文收；不会把两个 UDP 报文自动粘成一个，也不会像 TCP 那样天然出现“半包”语义。
- 但 `UDP` 面向数据报不等于绝对完整可靠，它仍然可能丢包、乱序、重复；如果接收缓冲区太小，还可能把一个报文截断。
- 即时聊天通常选 TCP 或基于 TCP 的 WebSocket，保证有序和可靠。
- 日志上报要看业务容忍度，审计强一致一般选 TCP，允许少量丢失才会考虑 UDP。
- 实时状态上报很多时候更看重“新鲜”，可考虑 UDP 加轻量补偿。
- 不能简单说“UDP 一定更快”，端到端效果还取决于重传、拥塞、链路质量和业务模型。
- 如果候选人已经说到“字节流”和“数据报”，下一步最自然的追问就是第 36 题：为什么 `TCP` 会有粘包半包，而 `UDP` 通常没有这个问题。

### 35. 粘包与半包：协议边界如何设计？

#### 参考答案要点

- TCP 是字节流，不保证应用层消息边界，粘包和半包不等于 TCP 丢消息。
- 这类问题主要出现在 TCP，不是因为 TCP “有缺陷”，而是因为它本来就只保证字节连续送达，不替应用保留一条条消息的边界。
- UDP 一般不会出现 TCP 这种“半包/粘包”语义，因为它是按数据报收发的；要么收到一个报文，要么丢掉，但不会把两个独立报文自动拼成一个业务消息流。
- 解决办法是应用层 framing，最常见的是“长度字段 + 消息体”。
- 读取循环要维护缓冲区，够一帧就解码，不够就继续读，剩余字节继续留在缓冲区。
- 固定长度、分隔符、长度字段各有场景，但生产里长度字段最常见。
- 如果候选人说到了“长度字段”，就可以继续追问第 43 题：长度字段按什么字节序编码，跨平台时为什么必须统一网络字节序。

### 36. 高并发 Socket 服务稳定性：如何避免雪崩？

#### 参考答案要点

- 要做连接生命周期治理：空闲超时、读写超时、心跳探活、指数退避重连。
- 要做背压：限制单连接发送队列，慢消费者要降级或断开。
- 要做容量规划：连接数、文件描述符、事件循环线程、端口资源都要有上限。
- 监控要覆盖在线连接数、建连成功率、异常关闭、重连次数、发送队列深度。

### 37. TCP 滑动窗口是干什么的？零窗口说明了什么？

#### 参考答案要点

- 滑动窗口让发送方不用每发一包都停下来等 ACK，可以连续发送一段数据，提高链路利用率。
- 接收窗口反映对端还能接收多少，拥塞窗口反映当前网络还能承受多少。
- 实际可发送量通常取两者更小值。
- 零窗口通常说明对端应用读慢了，接收缓冲区被打满，不一定是链路断了。

### 38. TCP 的重传、流量控制、拥塞控制分别在解决什么？

#### 参考答案要点

- 重传解决的是包丢失。
- 流量控制解决的是对端来不及接收。
- 拥塞控制解决的是网络路径承受不住当前发送速率。
- 快重传依赖重复 ACK，比等超时更快；超时重传更保守，但代价更大。

### 39. UDP 能不能做可靠传输？能的话怎么做？

#### 参考答案要点

- UDP 本身不保证送达、顺序、重传和去重。
- 如果业务需要“基本可靠”，常见做法是加序号、ACK、重传、滑动窗口、去重、必要时加 FEC。
- 但补得越多，就越像自研一个不成熟的 TCP，复杂度会迅速上升。
- 所以生产里一般优先评估成熟协议或现成框架。

### 40. 为什么 TIME_WAIT 不能随便去掉？太多了怎么办？

#### 参考答案要点

- `TIME_WAIT` 的作用主要是兜住最后 ACK，并隔离旧连接残留报文。
- 它通常出现在主动关闭方，短连接很多时数量高不一定是故障。
- 真正要警惕的是端口耗尽、建连失败率上升、连接风暴。
- 优化优先级通常不是先改内核参数，而是先减少频繁建连、使用连接池和长连接。

### 41. UDP 的单播、广播、组播，分别适合什么场景？

#### 参考答案要点

- 单播是一对一，最通用。
- 广播是一对整个网段，适合局域网设备发现，但不适合大范围使用。
- 组播是一对多，省带宽，适合同一份数据发给很多接收方。
- 但组播依赖网络设备和路由环境支持，公网环境很多时候不现实。

### 42. 大端序、小端序与网络字节序：协议字段该怎么解析？

#### 参考答案要点

- 大端序是高位字节放低地址，小端序是低位字节放低地址。
- 网络字节序通常约定为大端，重点不是谁“更先进”，而是跨平台通信必须统一表示。
- 协议里的长度字段、消息类型、序列号这类多字节字段必须明确字节序，不能依赖本机 CPU 内存布局。
- 如果客户端按小端写 `0x00000010`，服务端按大端读，就可能被解析成 `0x10000000`，拆包会直接错位。
- 常见实现方式：Java 用 `ByteBuffer.order(...)`，Go 用 `binary.BigEndian/LittleEndian`，C 用 `htonl/ntohl` 等转换函数。
- 这题很适合作为第 35、36 题之后的实现追问：前面先问协议模型和拆包，后面再问字段到底怎么编码，能更容易区分“会背概念”和“真做过协议”的候选人。

## 前端与 Spring

### 43. Vue 中 slot 是干什么用的？

#### 参考答案要点

- `slot` 本质是组件的内容占位机制。
- 它解决的是“组件结构固定，但局部内容由外部决定”的问题。
- 常见类型有默认插槽、具名插槽、作用域插槽。
- 作用域插槽的重点是数据在子组件，渲染方式交给父组件。

### 44. 什么是循环依赖？Spring 是怎么解决循环依赖的？

#### 参考答案要点

- 循环依赖是 A 依赖 B，B 又依赖 A。
- Spring 主要能解决的是单例 Bean 的属性注入循环依赖，不是所有情况都能处理。
- 核心思路是三级缓存，提前暴露早期对象引用，等依赖链走完再完成初始化。
- 构造器循环依赖、原型 Bean 循环依赖通常处理不了。
- 面试里最好补一句：能解决不代表这是好设计，很多时候还是应该拆依赖。

### 45. 如何理解 Spring Boot 中的 Starter？

#### 参考答案要点

- Starter 可以理解成一组场景化依赖打包。
- 它解决的是依赖组织问题，让你少手动拼装一堆基础组件。
- 真正的自动配置逻辑主要还是在自动配置类里，而不是 Starter 自己完成。
- 一句话总结：Starter 负责把常用依赖带进来，自动配置负责把这些依赖真正用起来。

### 46. Spring Boot 中为什么不推荐使用 `@Autowired` 注解？

#### 参考答案要点

- 更准确地说，不是不推荐 `@Autowired`，而是不推荐字段注入。
- 字段注入的主要问题是依赖不显式、测试不方便、对象不容易保持不可变。
- 现在更推荐构造器注入。
- 如果类里只有一个构造器，Spring 甚至可以不写 `@Autowired`。

### 47. Spring Boot 自动配置的实现原理是什么？

#### 参考答案要点

- 自动配置的核心是按条件装配。
- Spring Boot 启动时会加载一批自动配置类，再根据类路径、配置项、已有 Bean 等条件决定是否创建默认 Bean。
- 常见条件注解有 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty`。
- 一句话总结：依赖在、条件满足、你又没自己定义，Spring Boot 就帮你把默认配置装起来。

## 数据库深度与 Java 进阶

### 48. MySQL `EXPLAIN` 里的 `type` 怎么判断执行计划是否可接受？

#### 参考答案要点

- `type` 从优到劣常见有：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。
- 日常最关注的几类：
  - `ref` / `range`：说明用到了索引且效率不错，通常是可接受的。
  - `index`：全索引扫描，比全表好但在大数据量时仍可能慢。
  - `ALL`：全表扫描，一般要避免，尤其是大表上的高频查询。
- 判断执行计划不能只看 `type`，还要结合：
  - `key`：实际使用的索引。
  - `rows`：预估扫描行数，越小越好。
  - `Extra`：出现 `Using filesort` 或 `Using temporary` 时要警惕，排序/分组没走索引可能带来额外开销。
- 初中级标准答案里不要机械追求 `const`，而是要说明“核心链路尽量 `ref` 以上，明显出现 `ALL` 且 `rows` 很大时要优化”。

### 49. MySQL 主从延迟怎么排查？`binlog` 三种格式在一致性上有什么区别？

#### 参考答案要点

**排查思路**
- 先看 `SHOW SLAVE STATUS` 里的 `Seconds_Behind_Master`，它只能做粗略参考。
- 更准确的对比是看 `Master_Log_File` / `Read_Master_Log_Pos`（IO线程）和 `Relay_Master_Log_File` / `Exec_Master_Log_Pos`（SQL线程）的位点差。
- 常见根因：从库有大事务、慢 SQL、DDL 锁表、从库硬件差、单线程 SQL 回放瓶颈。
- 如果开了并行复制，还要看 worker 线程有没有等待或冲突。

**binlog 格式**
- `STATEMENT`：记录原始 SQL，日志量小，但某些非确定性函数（如 `UUID()`、`NOW()`）可能导致主从数据不一致。
- `ROW`：记录每行实际变更，日志量大，主从一致性最强，是最推荐的生产格式。
- `MIXED`：MySQL 自己判断，安全语句用 `STATEMENT`，不安全时用 `ROW`，折中方案。
- 一致性排序：`ROW` > `MIXED` > `STATEMENT`。

### 50. Java 8 的 `CompletableFuture` 相比原生 `Future` 解决了什么痛点？实际使用时怎么防止回调地狱和异常吞没？

#### 参考答案要点

- `Future` 的痛点：
  - `get()` 阻塞，不能方便地链式组合多个异步任务。
  - 缺少内置的异常处理和任务编排能力（如“等两个都完成再合并结果”）。
- `CompletableFuture` 的改进：
  - 支持链式调用：`thenApply` / `thenAccept` / `thenCompose`。
  - 支持组合：`thenCombine`、`allOf`、`anyOf`。
  - 支持显式完成和异常处理：`complete`、`exceptionally`、`handle`。

**防止回调地狱**
- 避免嵌套 `thenAccept`，改用 `thenCompose` 做扁平化链式调用。
- 把每个阶段拆成语义清晰的小方法，而不是把所有逻辑堆在一个 lambda 里。

**防止异常吞没**
- 链里至少留一个 `exceptionally` 或 `handle` 做兜底，否则未捕获异常可能被静默吞掉。
- 如果最终要同步拿到结果，用 `get(timeout, TimeUnit)` 或 `join()`，不要无限等待。
- 注意默认异步执行走的是 `ForkJoinPool.commonPool()`，任务量大时容易饱和；对核心链路建议传入自定义线程池。

## 容器、中间件与 Java 并发

### 51. `Dockerfile` 里的 `CMD` 和 `ENTRYPOINT` 有什么区别？生产镜像怎么分层优化减小体积？

#### 参考答案要点

**`CMD` vs `ENTRYPOINT`**
- `ENTRYPOINT`：容器启动的固定入口命令，不容易被直接覆盖（除非显式 `--entrypoint`）。适合把容器当成一个“可执行文件”来用。
- `CMD`：为 `ENTRYPOINT` 提供默认参数，或单独作为默认执行命令。如果用户 `docker run` 时带了命令行参数，会直接覆盖 `CMD`。
- 常见组合：用 `ENTRYPOINT` 写主程序路径，`CMD` 写默认参数，兼顾“开箱即用”和“灵活覆盖”。

**镜像分层优化**
- 层缓存：Docker 每一层被构建后只要该层指令输入不变，就能复用。把变动最小的指令放在前面，变动大的放在后面。
- 减少层数：能用一条 `RUN` 完成的操作尽量合并（如先 `apt-get update` 再 `install` 然后清理缓存），避免残留临时文件。
- 使用更小的基础镜像：生产环境尽量不用 `ubuntu:latest`，优先 `alpine`、`distroless` 或者 `jlink` 裁剪后的 JDK 基础镜像。
- 多阶段构建：把编译、打包和运行拆成不同阶段，最终镜像只保留产物和运行时，不带编译工具、源码和依赖缓存。

### 52. Nginx 反向代理时，502 Bad Gateway 和 504 Gateway Time-out 排查思路有什么区别？

#### 参考答案要点

**502 Bad Gateway**
- 含义：Nginx 作为网关，成功连到了上游，但上游返回了**不合法或无法处理**的响应。
- 典型根因：
  - 上游服务崩溃、进程退出、端口未监听。
  - 上游主动断开连接（如 PHP-FPM 子进程异常终止）。
  - 响应头过大，超过 Nginx `proxy_buffer_size`。
- 排查方向：直接访问上游地址看是否正常；看上游应用日志是否有异常；检查 Nginx `error.log` 里的 `upstream prematurely closed connection` 等关键字。

**504 Gateway Time-out**
- 含义：Nginx 在规定时间里**没等到上游的完整响应**。
- 典型根因：
  - 上游处理太慢（大事务、慢 SQL、死循环）。
  - 上游服务本身有健康，但网络丢包或延迟高。
  - Nginx 的 `proxy_read_timeout`、`fastcgi_read_timeout` 设置过短。
- 排查方向：压测/直接请求上游接口看 RT；检查上游 CPU/线程池/连接池是否被打满；逐步放大 Nginx 超时时间看是否只是配置问题。

**核心区别**
- 502 是“连上了但上游给了坏结果”，重点看**上游是否正常活着**。
- 504 是“等太久了没结果”，重点看**上游处理耗时和网络/超时配置**。

### 53. `ThreadLocal` 的实现原理是什么？为什么在线程池场景下特别容易发生内存泄漏？应该怎么正确使用？

#### 参考答案要点

**实现原理**
- 每个 `Thread` 对象内部维护了一个 `ThreadLocalMap`，key 是 `ThreadLocal` 的弱引用，value 是用户实际存储的对象。
- `ThreadLocal.set()` 时其实是往当前线程的 `ThreadLocalMap` 里写入键值对。
- 取数据时也从当前线程自己的 Map 里根据 `ThreadLocal` 实例查找，所以不同线程之间天然隔离。

**线程池下为什么容易内存泄漏**
- 线程池里的线程是复用的，不会随着任务结束而销毁。
- 如果用了 `ThreadLocal` 但没有 `remove()`，线程归还线程池后，`ThreadLocalMap` 里的 Entry 还会跟着这条线程一直存在。
- 虽然 `ThreadLocal` 的 key 是弱引用，会在 GC 时被回收，但 value 是强引用；如果 key 变成 null 而 value 没被清理，就会形成**无法访问但无法释放**的泄漏点。

**正确使用方式**
- 用完即清：在 `finally` 块里调用 `threadLocal.remove()`，确保无论业务是否异常都清理。
- 避免大对象长期存放：不要把整个请求上下文或超大对象长期塞在 `ThreadLocal` 里。
- 如果是 Tomcat/Jetty 等带线程池的 Web 容器，更要注意拦截器或过滤器里 `remove()` 的兜底。
- 面试里能说出 `ThreadLocalMap` + 弱引用 key + 强引用 value 的组合，才算真正理解泄漏根因。

## 容器、Java 基础与工程选型

### 54. Docker 容器的网络模式有什么区别？bridge 模式下同宿主机容器偶尔互通不通，怎么排查？

#### 参考答案要点

**四种常见网络模式**
- `bridge`：默认模式，Docker 为容器创建独立的 veth 接口并桥接到宿主机的 `docker0`，容器通过 NAT 访问外部网络。是最常见的隔离方案。
- `host`：容器直接使用宿主机的网络栈，没有独立的 IP，端口与宿主机共享。性能最好但隔离性最差。
- `none`：关闭容器网卡，只有 loopback，适合对网络要求极高的隔离场景。
- `container`：新容器共享另一个指定容器的网络命名空间，常见于 sidecar 模式（如日志采集、服务网格代理）。

**bridge 模式下同宿主机容器偶尔不通的排查**
- 先看容器是不是在同一自定义 bridge 网络里。默认 `bridge` 不支持通过容器名 DNS 解析，跨 compose 或手动启动时容易连到不同网桥。
- 检查 `iptables` / `firewalld` 是否拦截了网桥间流量，尤其是 CentOS 类系统默认策略较严。
- 看 Docker 的 `userland-proxy` 是否导致端口冲突或回环异常。
- 验证方法：
  - `docker network inspect <network>` 确认容器 IP 和子网。
  - 在容器里 `ping` / `curl` 对端 IP，排除 DNS 问题。
  - 宿主机抓包 `tcpdump -i docker0` 看包是否走到网桥。
- 能用自定义 bridge 尽量不用默认 bridge，自定义网络自带 DNS 和更好的隔离性。

### 55. 什么是 Java 中的 SPI 机制？JDBC、SLF4J 是怎么利用 SPI 的？和 Spring Boot 自动配置有什么关系？

#### 参考答案要点

**SPI 概念**
- SPI（Service Provider Interface）是 JDK 提供的一套服务发现机制，核心思想是“接口由上层定义，实现由下层扩展”，通过约定好的配置文件在运行期加载具体实现。
- 配置文件路径：`META-INF/services/接口全限定名`，文件内容是实现类的全限定名。
- 加载器：`ServiceLoader.load(Interface.class)`，在运行期读取配置文件并通过反射实例化实现类。

**JDBC 的例子**
- `java.sql.Driver` 是标准接口，各数据库厂商提供自己的实现（如 `com.mysql.cj.jdbc.Driver`）。
- JDBC 4.0 之后，驱动 jar 包里只要带了 `META-INF/services/java.sql.Driver`，`DriverManager` 就能自动发现，不需要再手动 `Class.forName()`。

**SLF4J 的例子**
- SLF4J 定义了日志门面接口，logback、log4j2 等实现jar通过 SPI 把自己注册进去，应用层只依赖门面，不直接依赖具体实现。

**与 Spring Boot 自动配置的关系**
- Spring Boot 的自动配置沿用了类似的“约定大于配置”思想，但它的加载机制不是 JDK SPI，而是基于 `spring.factories`（Spring Boot 2.7+ 开始推荐 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）。
- 面试官如果问“是不是 SPI”，要区分清楚：思想上类似，技术实现上 Spring Boot 有自己的加载器，不要混为一谈。

### 56. `ArrayList` 和 `LinkedList` 在时间复杂度上的差异大家都知道，那在实际工程里，除了遍历和随机访问，还有什么因素会影响你选哪个？

#### 参考答案要点

**时间复杂度是基础，不是全部。** 工程选型还要看下面几个维度：

1. **CPU 缓存友好性（Cache Locality）**
   - `ArrayList` 底层是连续数组，元素在内存中紧凑排布，CPU 预取命中率高，顺序遍历非常快。
   - `LinkedList` 节点分散在堆上，每个节点都要解引用指针，Cache Miss 严重，即使理论上 `get()` 是 O(n) 对 O(n)，实际遍历 `LinkedList` 往往比 `ArrayList` 慢一个数量级。

2. **内存占用与 GC 压力**
   - `ArrayList` 只存对象引用，额外开销小（当然数组本身可能有扩容冗余）。
   - `LinkedList` 每个节点都要维护 `prev` / `next` 两个指针，对象头开销大；节点数多时堆内存和 GC 遍历成本显著上升。

3. **随机插入删除的“理论”与“现实”**
   - 虽然 `LinkedList` 随机插入是 O(1)，但前提是已经定位到节点。如果通过索引插入，需要先 O(n) 遍历找到位置，整体并不快。
   - 真正适合 `LinkedList` 的场景是：频繁在头尾插入/删除，或者需要利用它实现队列/双端队列，且数据量不大。

4. **工程结论**
   - 现代 Java 工程里，绝大部分场景默认选 `ArrayList`；除非明确需要双端队列语义，或者频繁头尾操作，否则不推荐 `LinkedList`。
   - 面试时能说清“Cache Locality 和 GC 压力”比只会背 O(1)/O(n) 更能体现工程思维。

## 高频业务场景与根因追问

### 57. 抽奖系统用 Redis + Lua 扣库存，为什么能保证并发下的正确性？

#### 参考答案要点

**1. Redis 单线程执行模型是前提**
- Redis 服务端处理命令是**单线程串行执行**的（Redis 6.0+ 多 IO 线程仅负责网络读写，命令执行仍是单线程）。
- 这意味着任一时刻不会有两个客户端命令同时修改同一份数据，天然避免了线程竞态。

**2. Lua 脚本在 Redis 里具备原子性**
- Lua 脚本被发送到 Redis 后，会被当作一个**不可分割的执行单元**。
- 执行期间不会插入任何其他客户端命令，直到脚本全部执行完毕。
- 所以 `判断库存 > 0 → 扣减库存 → 记录日志` 在 Redis 视角里是一步完成的，中间不存在被其他请求打断的窗口。

**3. 为什么普通命令序列不行？**
- `GET stock` → 应用层判断 → 再发 `DECR`，这是**三个独立的网络往返**。
- `GET` 和 `DECR` 之间，其他客户端可能已经把库存扣光，导致超卖。

**4. 为什么不推荐 `WATCH` + `MULTI`/`EXEC`？**
- `WATCH` 是乐观锁，高并发写冲突下会频繁失败重试，吞吐量急剧下降。
- Lua 脚本是**一次执行、没有重试风暴**。

**5. 这个方案的风险和边界**
- **阻塞主线程**：Lua 不能写太重，大量循环会阻塞整个 Redis 实例。
- **集群限制**：Redis Cluster 要求 Lua 访问的所有 key 在同一 slot，否则报错。通常用 hash tag（如 `{lottery}:stock`）强制同 slot。
- **持久化一致性**：Redis 扣减成功仅代表内存数据变了，如果此时宕机且没来得及落盘/同步从库，重启后库存可能回退。核心业务一般要配合 MySQL 最终一致性或对账兜底。

#### 追问建议

1. **"把 Lua 脚本换成在客户端用 Shell 脚本执行同一组 Redis 命令，能不能保证同样的正确性？"**
   → **不能**。Shell 脚本在客户端执行时，发出去的仍是多条独立网络请求，Redis 服务端会把它们当成多个独立命令依次处理，完全可能被其他客户端命令穿插，原子性被破坏。

2. **"Redis 扣减成功，但后面异步写数据库时失败了，库存已经少了但实际没发奖，怎么兜底？"**
   → 预期提到：**异步对账、定时扫描差异、预扣库存超时回滚、补偿机制**等。
