#### 3. 去重、分片与存储

##### 如何利用 MD5 配合分布式锁做内容级别去重

参考回答：

> 我们会先对文件内容计算 MD5，把它当作内容指纹。请求到来后先查是否已有同 MD5 的成功记录；如果没有，再基于 `md5` 获取分布式锁，防止多个请求同时处理同一文件。拿到锁后会二次校验数据库或缓存，确认没有被其他节点处理，然后再创建解析任务。这样可以避免重复解析，节省存储和模型调用成本。锁释放要放在 finally，并且任务表要有唯一约束做最终兜底。

##### Redis 的分片状态是怎么设计的？分片大小为什么是 5MB

参考回答思路：
- 状态设计：`INIT / UPLOADING / UPLOADED / MERGING / SUCCESS / FAIL / EXPIRED`
- 每片记录：片序号、ETag、大小、上传时间、重试次数。
- 5MB 依据：
  - 兼顾失败重传成本和请求数。
  - 太小会导致分片过多、元数据膨胀。
  - 太大会拉高单次重传成本和超时概率。

##### MinIO 里未合并成功的残余分片文件，怎么处理

参考回答：

> 这类残余分片不能只靠人工清理，通常要做两层兜底。第一层是在合并失败时回写任务状态，并记录失败原因和重试次数；第二层是定时清理任务，扫描长时间未完成且无活跃会话的分片，确认主文件不存在后删除残片。另外要把清理动作做成幂等，避免误删正在上传的分片。

#### 4. AI 提效与 AICR

##### 你平常怎么使用 AI

建议把这个问题和“AI 怎么帮你们提效”放在一起问，但更偏个人工作流。

第一层先问使用范围：
- “你平常用 AI 做什么？是写页面、补 CRUD、写单测、查文档，还是分析日志和设计方案？”

### 三、高并发、缓存、MQ 与分布式一致性

#### 5. 营销与库存场景

##### 电商系统里如何防止超卖

参考回答：

> 防超卖一般不会只靠一层。常见做法是入口先限流和资格校验，缓存层做预扣减或原子扣减，数据库层再用条件更新或乐观锁兜底，异步链路通过消息和对账做最终一致性补偿。这样即使某一层出现异常，也能通过补偿机制把库存纠正回来。

##### 超卖怎么保障数据的最终一致性

参考回答：

> 我一般不会只靠单点方案解决超卖，而是做分层控制。入口层先做限流和资格校验，缓存层可以做预扣减或原子扣减，数据库层通过乐观锁或条件更新兜底，异步链路再做最终一致性补偿。即使中间某个环节失败，也能通过消息重试、状态对账和补偿任务把库存拉回正确状态。

##### 你说的库存这块其实就是乐观锁，对吧？当初这么设计是考虑性能优化吗

参考回答：

> 是的，本质上就是基于版本号或条件更新的乐观锁。选择它主要是因为读多写少且冲突可接受，比悲观锁更轻，吞吐更高。它不只是性能优化，也是为了减少锁等待和数据库阻塞。不过如果热点冲突非常高，单纯乐观锁会有大量重试，需要继续往前做分段库存、异步削峰或 Redis 预扣减。

##### 你提到的优惠券规则引擎是什么

参考回答：

> 我理解这里的规则引擎不是很重的通用引擎，而是把发券条件从硬编码里抽出来，做成可配置的规则组合。比如用户新老客身份、活动时间、渠道、门槛、库存和互斥条件，都可以通过规则配置去判断是否满足发券条件。这样做的好处是活动变更时不用频繁改代码发版，业务灵活性更高，但实现上要注意规则优先级、冲突处理、灰度发布和回溯能力。

##### 延迟队列处理超时订单时，怎么通过乐观锁解决支付关单冲突

参考回答：

> 关键点是状态更新要带条件。比如延迟队列消费到超时订单时，不是直接关单，而是执行 `update ... where order_id = ? and status = WAIT_PAY`。如果用户已经支付成功，状态就不再是待支付，更新会影响 0 行，这样就避免了支付成功和自动关单之间的并发冲突。

##### 单用户超领与库存超发怎么解决

单用户超领：
- 用户维度唯一约束。
- Redis 原子计数。
- 业务状态幂等校验。

库存超发：
- Redis Lua 原子扣减。
- 数据库条件更新。
- 异步补偿和对账。

##### 高并发下乐观锁会不会有性能问题，如何继续优化

参考回答：

> 会。有热点时会出现大量更新失败和重试，数据库 CPU 会被无效竞争吃掉。优化一般有三层：第一层是把热点流量挡在前面，比如资格预校验、限流、分桶；第二层是把扣减前移到 Redis 或分段库存；第三层是异步化，把同步强一致改造成最终一致，再配合补偿和对账。

#### 6. 异步化与发券可靠性

##### 注册发券从同步改异步后，怎么保证券成功发放

回答要点：
- 先落业务记录。
- 再发消息，不直接依赖瞬时发送成功。
- 消费端幂等。
- 失败可重试。
- 最终有对账补偿。

##### 分布式链路异步化改造的背景、落地和收益

回答结构：
1. 背景：同步链路长、RT 高、耦合重、下游故障放大。
2. 落地：拆成事件驱动节点，用 MQ 串联。
3. 关键：状态机、幂等、重试、死信、监控。
4. 收益：接口更快、系统更稳、扩容更容易。

##### MQ 重试会不会导致多发券，怎么保证不重发

参考回答：

> 会，所以消费端必须按业务唯一键做幂等。常见做法是给每次发券定义业务唯一流水，比如用户 ID + 活动 ID + 触发场景，再在数据库加唯一索引。消费者先查或插幂等记录，已经处理过就直接返回。这样即使消息重复投递，也不会重复发券。

##### 达到最大重试次数依然失败怎么办

标准回答：
- 进入死信队列或失败表。
- 触发告警。
- 人工 / 定时补偿。
- 必要时给用户展示“处理中”。

##### MQ 消息积压怎么监控和处理

回答要点：
- 监控 backlog、消费速率、失败率、重试次数、处理耗时。
- 快速处理：
  - 扩消费者实例。
  - 提升批量消费能力。
  - 做消息降级和优先级隔离。
  - 排查是否下游慢 SQL 或外部接口卡住。

##### RabbitMQ 怎么实现消息不丢失和不重复消费

不丢失：
- 生产者 confirm。
- 消息持久化。
- 队列和交换机持久化。
- 消费者手动 ACK。

不重复：
- 消费端幂等。
- 唯一键去重。
- 重试不改业务语义。

如果候选人只回答“MQ 用过”，建议继续追问：
- “你为什么要引入 MQ？是解耦、削峰、异步化，还是顺序消费需求？”
- “你们怎么保证消息不丢失？生产者、Broker、消费者各自做了什么？”
- “重复消费怎么处理？有没有幂等键或唯一约束？”
- “消息积压时你怎么判断是生产过快还是消费过慢？”
- “失败重试和死信是怎么设计的？最大重试后怎么办？”

你想听到的关键信号：
- 能分生产端、Broker、消费端三段回答。
- 能说出幂等、ACK、重试、死信这些关键机制。
- 能结合自己的业务场景，而不是只背 MQ 八股。

#### 7. Redis、锁与缓存

##### Redis 和分布式锁如何设计数据结构

参考回答：

> 基础分布式锁最常见的结构就是 `String`。key 一般按业务维度设计，比如 `lock:order:123`、`lock:coupon:userId:activityId`，value 存唯一请求标识，例如 UUID 加线程标识，用来保证解锁时不会误删别人的锁。再配合过期时间避免死锁。如果还要做锁重入、续期次数、等待队列这类扩展能力，可以额外用 `Hash` 或独立 key 存元数据，但锁本体通常 `String + NX + EX/PX` 就够了。

##### Redis 缓存击穿为什么用逻辑过期

参考回答：

> 热点 key 到期时，如果直接删除，就会有大量请求同时打到数据库。逻辑过期的思路是缓存数据本身不马上删，而是给它带一个逻辑过期时间。读请求发现过期后，先返回旧值，再由后台线程异步刷新。这样能显著降低热点失效瞬间的抖动，代价是短时间内会读到旧数据，所以更适合可接受短暂旧值的场景。

##### Redis 持久化怎么配置

标准答案：
- RDB：定期快照，恢复快，但可能丢最近数据。
- AOF：按命令追加，数据更完整。
- 生产一般：AOF + 合理刷盘策略，必要时配合 RDB。

##### Lua 脚本执行到一半 Redis 挂了会怎样

关键结论：
- Redis 执行 Lua 是原子的，要么脚本完整执行完，要么没有对外部命令插入。
- 但“原子”不等于“绝不丢数据”。
- 如果主节点刚执行完内存修改就宕机，而持久化和主从同步还没完成，重启后数据可能回退。

##### Redis 基础数据类型有哪些

答法：
- String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、Stream。
- 面试里优先讲前五个，再补充扩展类型。

##### Redisson 看门狗一直续期，锁还能释放吗

回答：

> 能，只要持锁线程最终正常执行完 `unlock`。看门狗只是为了避免业务执行时间超过初始租约导致锁提前过期，它会持续续期，但不会替代主动解锁。如果线程卡死、进程崩溃或根本没走到 `unlock`，那就只能等看门狗停止续期后让锁自然过期。

#### 9. Java 基础

##### Java 泛型

参考回答：

> Java 泛型主要是为了解决编译期类型安全问题，减少强转。它本质上是类型擦除，运行期大多数泛型信息会被擦掉，所以常说 Java 是伪泛型。比如 `List<String>` 和 `List<Integer>` 在运行时的原始类型都是 `List`。

- 能结合真实代码场景，而不是只背定义。

如果想继续压深一点：

##### Java 泛型如何“解除”或绕过泛型限制

参考回答：

> 严格说不是“解除泛型”，而是绕过编译期约束。因为 Java 泛型本质是类型擦除，运行时大多数泛型信息已经没了，所以可以通过原生类型、反射等方式绕过编译检查。比如把 `List<String>` 赋给原生 `List` 后，再插入一个 `Integer`，编译器未必拦得住，但这样会把类型安全问题延后到运行期。面试里最好主动补一句：这能说明泛型约束主要发生在编译期，不代表工程上应该这么写。

##### Java 反射

参考回答：

> 反射就是在运行时获取类信息并操作类、方法、字段的能力。优点是灵活，比如框架可以基于注解和反射做依赖注入、ORM 映射；缺点是性能比直接调用低，可读性也弱，所以业务代码里一般不会滥用。

##### 数组和列表怎么相互转换

答法：
- 数组转 List：`Arrays.asList(arr)`，但它返回的是定长视图。
- List 转数组：`list.toArray(new Type[0])`。
- 基本类型数组不能直接得到 `List<Integer>`。

##### Stream 流

答法：
- Stream 是声明式数据处理。
- 常用操作：`filter`、`map`、`collect`。
- 优点是表达清晰，缺点是过度链式时调试不友好。

##### Java 中 `finally` 里直接 `return` 会怎样

参考回答：

> 如果 `finally` 里直接 `return`，它会覆盖 `try` 或 `catch` 里原本的返回值，连异常也可能被吞掉，所以这是非常不推荐的写法。面试里最好直接给结论：`finally` 更适合做资源释放，不适合写 `return`。

##### 线程和进程的区别

一句话：
- 进程是资源分配单位，线程是 CPU 调度单位。
- 同进程线程共享内存，切换成本低；进程隔离更强，切换成本更高。

##### 协程 / Java 虚拟线程

答法：
- 协程是用户态轻量并发单元。
- Java 虚拟线程由 JDK 调度到少量平台线程上，适合大量阻塞型任务。
- 优点是降低线程占用成本，但不等于对所有 CPU 密集型任务都更快。

### 五、MySQL、MyBatis 与数据库优化

#### 12. 索引与慢 SQL

##### MySQL 索引结构是什么

标准回答：

> InnoDB 的主流索引结构是 B+ 树。主键索引是聚簇索引，叶子节点直接存整行数据；二级索引叶子节点存主键值，回表时再去聚簇索引取完整记录。

##### 如何设计一个比较好的索引

参考回答：

> 好索引不是字段都建上，而是围绕真实 SQL 设计。一般先看高频查询的过滤条件、排序条件和返回字段，再决定单列还是联合索引。联合索引要遵守最左前缀原则，并尽量让高选择性字段靠前；如果能做成覆盖索引，还能减少回表。设计后还要用 `EXPLAIN` 验证，否则很容易出现“以为命中索引，实际仍然扫描很多行”的情况。

##### 索引失效场景

常见场景：
- 对索引列做函数或计算。
- 隐式类型转换。
- 联合索引不满足最左前缀。
- `like '%xx'`。
- 选择性太差，优化器认为全表更划算。
- 范围查询后续列利用受限。

##### 加了索引还走全表扫描怎么排查

答法：
1. `EXPLAIN` 看执行计划。
2. 看索引是否命中。
3. 看统计信息是否准确。
4. 看 SQL 是否有函数、类型转换、范围条件。
5. 看返回行数是否太大。

##### 慢 SQL 优化怎么说

回答结构：
- 先定位：慢日志 + EXPLAIN。
- 再分析：扫描行数、回表、排序、临时表。
- 再优化：索引、SQL 改写、分页方式、冷热分离。

如果候选人只回答“加索引”，可以继续追问：
- “你先说慢在哪里，是扫描行数太大、回表太多，还是排序 / 临时表 / 深分页问题？”
- “`EXPLAIN` 看到了什么？`type`、`key`、`rows`、`Extra` 是什么情况？”
- “为什么原来的索引没有生效？是函数、类型转换、最左前缀没走到，还是优化器判断不划算？”
- “优化后指标变化是什么？”

好的回答信号：
- 能结合执行计划说问题。
- 能区分索引问题和 SQL 写法问题。
- 能给出优化前后的数据对比。

##### 分页查询相关

要点：
- 深分页 `limit offset` 会越来越慢。
- 可用覆盖索引、延迟关联、基于主键游标翻页。

#### 13. 事务、隔离级别与 MVCC

##### MySQL 默认事务隔离级别

结论：
- InnoDB 默认是可重复读。

##### 事务可以嵌套吗

参考回答：

> 如果从数据库原生能力看，MySQL 并不支持真正意义上的事务嵌套。你在一个事务里再 `begin`，本质上还是同一个事务上下文。工程里常说的“嵌套事务”更多是框架层语义，比如 Spring 的传播行为。像 `REQUIRES_NEW` 是挂起外层事务再开一个新事务，`NESTED` 更接近基于保存点 `savepoint` 的局部回滚，所以面试时要先分清是在问数据库能力还是在问 Spring 事务传播。

##### 不同隔离级别下乐观锁表现有区别吗

答法：
- 乐观锁本身依赖版本号或条件更新，不直接依赖隔离级别。
- 但不同隔离级别会影响你读到的数据版本和并发行为。
- 一般只要更新条件写得对，核心正确性仍然能保证。

##### MySQL 事务怎么实现

要点：
- 原子性靠 undo log。
- 持久性靠 redo log。
- 隔离性靠锁和 MVCC。
- 一致性是前面机制与业务约束共同保证。

##### 可重复读和读已提交怎么实现

答法：
- 主要依赖 MVCC 和 Read View。
- 读已提交每次读取都可能生成新的 Read View。
- 可重复读通常在事务第一次快照读时生成，并在事务内复用。

##### Read View 的作用

一句话：
- 用来判断当前事务能看到哪个版本的数据。

##### MVCC 在 InnoDB 里怎么实现

核心点：
- 每行有隐藏字段，如事务 ID、回滚指针。
- 旧版本通过 undo log 串起来。
- 读取时结合 Read View 沿版本链找可见版本。

#### 14. MyBatis

##### `#` 和 `$` 的区别

标准回答：

> `#{}` 是预编译参数，占位后由驱动安全绑定，能防 SQL 注入。`${}` 是字符串直接拼接，适合表名、排序字段这类不能参数化的位置，但有注入风险。值条件优先使用 `#{}`。

##### 防 SQL 注入必须用哪个

结论：
- 绝大多数值参数必须用 `#{}`。
- 如果必须用 `${}`，一定要白名单校验。

- 生命周期包括实例化、属性注入、初始化、销毁。
- 常见作用域有 singleton、prototype、request、session。
- 常见扩展点有初始化回调、销毁回调、`BeanPostProcessor`、`BeanFactoryPostProcessor`。

##### Spring Boot 常见注解举例说明

参考回答：

> 可以按类别讲。启动类常见 `@SpringBootApplication`；组件扫描和注入常见 `@Component`、`@Service`、`@Repository`、`@RestController`；配置类常见 `@Configuration`、`@Bean`、`@ConfigurationProperties`；Web 层常见 `@RequestMapping`、`@GetMapping`、`@PostMapping`；事务和异步有 `@Transactional`、`@Async`。面试时最好别只报名字，至少挑两三个说清具体使用场景。

##### Spring Boot 启动后自动执行业务代码怎么实现

常见答法：
- `ApplicationRunner`
- `CommandLineRunner`
- `@PostConstruct`

更稳妥的是前两者，因为更贴近启动完成后的业务初始化。

##### XXL-JOB 和 Spring 定时任务有什么区别

参考回答：

> Spring 自带定时任务适合单体或简单场景，实现轻，但缺少可视化调度、失败重试、执行日志和分布式管理能力。XXL-JOB 更适合多实例和生产环境，支持调度中心、任务管理、告警和路由策略，所以在需要统一管理任务时更合适。

##### 如果要自己实现一个定时任务

答法：
- 简单场景用 `@Scheduled`。
- 分布式场景要加分布式锁或调度中心，避免多实例重复执行。

#### 16. 架构与工程实践

##### IPv6 比 IPv4 有哪些优点

参考回答：

> 最核心的优势是地址空间大得多，能支撑海量设备接入。除此之外，IPv6 还改进了地址自动配置能力，减少了对 NAT 的依赖，报文头设计更简化，路由聚合能力也更好。面试里可以补一句：IPv6 的核心价值更多在地址规模和端到端能力，不是简单理解成“天然更快”。

##### 微服务有过接触吗

可以这样答：

> 有基础接触，理解它的核心不是把服务拆小，而是围绕业务边界拆分，并解决服务注册发现、配置管理、链路追踪、容错和部署治理等问题。我的实际经历更多还是在具体服务模块开发和调用链优化上。

如果候选人回答“接触过”，建议继续追问：
- “你具体参与的是哪部分？服务拆分、服务调用、注册发现、配置中心、网关、链路追踪还是熔断限流？”
- “在微服务场景下你遇到过什么实际问题？比如超时重试、链路追踪困难、配置不一致、接口幂等、分布式事务。”
- “你做过的工作更偏业务开发，还是偏治理能力建设？”

你想听到的关键信号：
- 能说出自己真正参与的部分，而不是泛背概念。
- 能结合一个具体问题说明微服务带来的复杂度。
- 不会把“项目拆成几个模块”误说成成熟微服务治理。

- 代码评审。

- 指标观察与回滚预案。

- 开发联调。
- CR。
- 测试。
- 发布复盘。

#### 17. 权限模型

##### RBAC 和 ABAC 的区别

标准回答：

> RBAC 是基于角色的访问控制，用户先绑定角色，角色再绑定权限，优点是简单清晰、易维护。ABAC 是基于属性的访问控制，会综合用户属性、资源属性、环境属性做判断，表达能力更强，但规则设计和维护复杂度也更高。

#### 20. 并发场景题

##### 多线程并发从同一个 API 获取数据，如何设计

参考回答：

> 这题要先问清目标，是为了提吞吐、降总耗时，还是做批量抓取。一般设计上我会先控制并发度，而不是无脑开线程。可以用线程池统一管理任务，结合超时、重试、熔断和限流，避免把下游 API 打挂。如果结果可缓存，可以先做本地缓存或分布式缓存，避免同一数据被重复请求；如果多个线程请求的是同一个 key，还可以做请求合并，避免击穿。最终还要落到监控上，看成功率、RT、超时率和线程池堆积情况。

## AI 后端开发面试题

说明：
- 本文对应 `AI后端开发面试题.md`，给的是参考答法，不是标准答案。
- 项目数据、模型名称、技术栈、QPS、耗时、成本、成功率这类信息必须替换成真实值。
- 面试回答尽量遵循一个顺序：先结论，再拆原理，最后落到你做过的事。

### 一、实习与项目拷打

#### 1. 实习拷打

##### 自我介绍一下，重点讲你做的 AI 后端 / Agent 相关工作

参考模板：

> 我是 [学校 / 专业] 的 [姓名]，实习期间主要做 AI 后端开发，参与了 [项目名称]。我负责的模块主要是 [任务编排 / 工具调用层 / 记忆管理 / 异步任务 / 结果落库]。这个系统的目标是把用户输入转成一套可执行的 AI 流程，并稳定输出结构化结果或可交付动作。我比较关注状态管理、工具编排、可观测性和生产稳定性。

##### 你在团队里的角色是什么，负责哪些模块

回答要点：
- 不要把自己说成整个平台 owner，按真实职责说清楚。
- 最好只讲 2 到 3 个模块，例如任务状态机、工具执行层、记忆召回层。
- 每个模块最好带一个结果，例如“把失败任务的可恢复率做上去”。

##### 你做的项目解决什么问题，给业务带来了什么价值

答法：

> 我们做的不是简单接一个模型 API，而是把用户请求变成一个可编排、可观测、可恢复的执行流程。业务价值主要有三类：第一，减少人工处理成本；第二，提升复杂任务的自动化率；第三，让结果输出更稳定、可追踪、可复盘。

##### 你最有成就感的一次优化是什么

回答结构：
1. 先讲背景，例如串行链路太长、失败任务不可恢复、模型成本太高。
2. 再讲你做了什么，例如拆异步阶段、补状态机、做结果缓存。
3. 最后用真实指标收尾，例如平均耗时下降、成功率提升、单任务成本下降。

#### 2. 项目拷打

##### 讲讲你们的 AI 项目 / Agent 平台整体目标和典型使用场景

参考模板：

> 这个平台的目标是把用户目标拆成可执行任务，再通过模型、工具和业务系统完成闭环。典型场景是 [请替换：知识问答 / 数据分析 / 工单处理 / 代码辅助 / 内容审核 / 多步骤业务执行]。后端的核心不是“让模型回答”，而是保证规划、执行、重试、落库和观测这些环节稳定可控。

##### 从用户发起请求到结果返回，完整链路是怎样的

建议按这个顺序讲：
1. 接收用户请求并做参数校验、鉴权、限流。
2. 创建会话和任务记录，写入初始状态。
3. 拉取短期上下文、长期记忆、必要业务数据。
4. 由模型规划或命中固定工作流。
5. 执行工具调用或业务动作。
6. 聚合中间结果，必要时补追问或重规划。
7. 生成最终回复或结构化输出。
8. 记录日志、指标、执行轨迹和可复盘数据。

##### 哪些环节是同步返回，哪些环节必须异步化

参考思路：
- 同步：参数校验、快速检索、简单总结、低成本工具调用。
- 异步：长链路规划、多工具串并行执行、文件处理、外部系统慢调用、高成本模型任务。
- 原因：避免请求阻塞太久，也方便做重试、恢复和用户侧进度展示。

### 二、Agent 流程与架构设计

#### 3. 任务编排与状态流转

##### 状态机是用于干什么的

参考回答：

> 状态机的核心作用是把一个长链路任务拆成确定的阶段，让任务有明确状态、转移条件和失败处理策略。这样做的价值不是“好看”，而是为了支持幂等、重试、恢复、观测和问题排查。没有状态机的话，复杂 Agent 流程很容易变成一坨 if else，线上出了问题很难知道卡在哪一步。

##### 你们的任务状态一般有哪些

可以按你们实际情况讲，例如：
- `INIT`
- `PLANNING`
- `WAITING_USER`
- `EXECUTING_TOOL`
- `AGGREGATING`
- `SUCCESS`
- `FAILED`
- `CANCELLED`

加分点：
- 每个状态要有进入条件和退出条件。
- 失败不只是一个 `FAILED`，最好还能记录失败阶段、错误码、重试次数。

##### 多步骤任务里，如何处理部分成功、部分失败

答法：

> 我们不会把多步骤任务视为一个黑盒整体成功或失败，而是把每个阶段的输入、输出、状态和错误原因都记录下来。这样某一步失败时，可以只重跑失败阶段，而不是整条链路从头开始。对于已经落库或已经发起外部动作的步骤，还要配合幂等键和补偿逻辑，避免重复执行。

#### 4. 规划、执行与追问

##### 在流程中，AI 是否会再次询问用户

参考回答：

> 会，但不是默认每轮都问。只有在目标不清楚、缺关键参数、或者继续执行的风险明显高于追问成本时，系统才会进入 `WAITING_USER` 这类状态。能靠已有上下文和后端规则补齐的信息，就不要反复打断用户。

##### 在规划中，AI 是否会进一步细化动作

参考回答：

> 会。复杂任务不能只停在“先查再算再输出”这种粗粒度计划，通常会在进入执行前，把计划细化成更小的步骤，比如先检索哪些信息、调用哪些工具、需要哪些前置参数、哪些步骤可以并行。这样后端才能更稳定地执行、重试和观测。

##### 为什么需要 Planner / Executor / Replanner 这样的拆分

回答要点：
- Planner 负责拆目标，不直接碰真实副作用。
- Executor 负责执行确定动作，强调可控和可观测。
- Replanner 在执行结果不满足预期时重新调整计划。
- 这样做比“一个模型全包”更容易调试，也更利于权限隔离。

##### 什么情况下由模型自由规划，什么情况下走固定工作流

建议答法：

> 如果任务开放度高、路径不确定，适合先让模型做规划；如果任务强约束、高风险、流程固定，比如支付、审批、资源变更，就更适合走确定性工作流。我的理解是模型适合负责“理解和拆解”，关键副作用操作还是应该由后端规则接管。

#### 5. 工具调用与结果回收

##### 模型决定调用工具后，后端具体做了哪些事情

回答顺序：
1. 校验工具名和参数是否合法。
2. 校验当前会话、用户、租户是否有权限。
3. 生成调用记录和 trace id。
4. 执行工具，处理超时、异常和重试。
5. 对返回结果做裁剪、结构化、脱敏。
6. 写回中间状态，再决定是否继续推理。

##### 一个工具返回结果过大时，怎么裁剪上下文

参考回答：

> 不能把工具原始输出无脑喂回模型。我一般会按三层处理：第一层保留结构化摘要，第二层保留关键字段，第三层把完整原始结果落持久化存储，只把引用或片段交给模型。这样既能控 token，又方便后面追溯原始结果。

##### 如何防止模型反复调用同一个工具造成死循环

回答要点：
- 给工具调用设置最大轮次或最大深度。
- 对相同参数的重复调用做去重或缓存。
- 对连续失败的工具做熔断。
- 如果多轮调用仍无新增信息，强制退出并返回原因。

### 三、框架与技术选型

#### 6. 框架与语言

##### 你们使用的是什么框架？为什么选它

不能硬编，建议按这个结构答：
- 先说真实框架，例如自研编排层、LangGraph、Spring AI、Semantic Kernel、工作流引擎等。
- 再说选择理由，例如状态编排清晰、工具接入方便、和现有技术栈兼容、便于生产治理。

##### 整体技术栈是 Python 还是 Java？为什么这样分工

参考答法：

> 我们一般不会把问题说成二选一，而是按职责分层。模型编排、实验验证、数据处理这层更适合 Python，因为生态快；业务服务、鉴权、交易链路、稳定性要求高的服务更适合 Java，因为工程化和存量基础更强。关键不是语言本身，而是接口边界清晰、状态一致、日志可追踪。

##### 如果让你从 0 到 1 设计一套 AI 后端，你会先拆哪些核心模块

建议答案：
1. 会话与身份层。
2. Prompt 与上下文构造层。
3. 规划与执行编排层。
4. Tool / MCP 接入层。
5. 记忆与检索层。
6. 任务队列与状态机。
7. 观测、审计、限流和成本治理。

#### 7. 外部方案参考

##### 你们参考过 Claude Code 吗

安全答法：

> 参考过它的一些产品和工程思路，比如任务分解、工具调用约束、沙箱安全确认、执行轨迹可见这些点。但我不会说成完全复刻，因为不同团队的目标不一样，我们更关注的是和自己业务系统、权限体系、任务状态机怎么结合。

##### 你怎么看待“现成框架很快能跑，但难以落生产”

参考回答：

> 我认同这个问题。很多框架把“能调通模型和工具”解决得不错，但生产系统真正难的是状态持久化、失败恢复、权限控制、审计、压测、降级和成本治理。所以我的习惯是把开源框架当能力底座，而不是把它直接当生产答案。

### 四、记忆与上下文管理

#### 8. 记忆设计

##### 对于记忆管理，你们有什么想法

参考回答：

> 我理解记忆不是“把所有历史都塞进去”，而是让系统在后续任务里用得上正确的信息。短期记忆更像当前任务上下文，长期记忆更像跨会话保留下来的用户画像、偏好、常用约束或稳定事实。真正难点不在存，而在什么时候写、写什么、什么时候召回。

##### 短期记忆和长期记忆分别存什么

回答要点：
- 短期记忆：最近几轮对话、当前计划、工具中间结果、未完成任务状态。
- 长期记忆：稳定偏好、历史结论、用户常用配置、经过提炼的高价值事实。
- 不建议把原始长对话直接全部当长期记忆。

##### 记忆是在什么时候写入的？每轮对话都写吗

参考答法：

> 不会每轮都写。一般只有在识别出稳定偏好、明确事实、重复出现的重要约束、或者对后续任务有复用价值的信息时才写入。否则很容易把临时上下文、错误结果甚至幻觉内容写进长期记忆，后面越用越乱。

##### 如何判断一段信息值得长期保留

回答要点：
- 是否稳定，不会短时间变化。
- 是否跨任务复用。
- 是否经过校验，来源可信。
- 是否能用结构化形式表达。

#### 9. 上下文窗口与压缩

##### 你们怎么控制上下文长度

参考回答：

> 我们不会简单按轮次硬截断，而是做分层控制。系统提示词、当前任务目标、最近关键交互、必要记忆和工具摘要优先级最高；冗长历史会做摘要或引用化处理。目标是把最相关的信息留在窗口里，而不是把所有历史平均对待。

##### 历史对话太长时，是截断、摘要还是分层压缩

建议答法：

> 三种方式都会用。时效性强但价值低的内容直接截断；重复但有价值的内容做摘要；工具原始输出和长文档通常只保留摘要和引用。分层压缩比一刀切摘要更稳，因为它能保留不同信息的粒度。

##### 如何避免摘要把关键信息压没

回答要点：
- 对关键字段做结构化保留。
- 对用户硬约束设白名单，禁止在摘要时丢失。
- 摘要结果也要可追溯到原文。
- 对高风险任务宁可保留更多原文，也别过度压缩。

### 五、Skill、Tool 与 MCP

#### 10. Skill 与工具抽象

##### 你对 Skill 有什么了解

参考回答：

> 我理解 Skill 是一种可复用的能力封装，里面不只是一个 prompt，还应该包含适用场景、输入输出约束、调用步骤、可能依赖的工具，以及必要的安全边界。它本质上是在把“怎么做一类事”沉淀成标准能力，而不是每次都临时写 prompt。

##### 一个 Skill 最少应该包含哪些信息

建议答法：
- Skill 名称和目标。
- 适用场景与边界。
- 输入输出约束。
- 所需工具或资源。
- 执行步骤或提示词模板。
- 失败处理和风险限制。

##### 什么时候该做 Skill，什么时候直接写死在业务流程里

回答原则：
- 高复用、跨场景、可参数化的能力适合做 Skill。
- 强业务绑定、强副作用、流程固定的动作更适合写在后端工作流里。
- Skill 更像能力模板，业务流程更像确定性编排。

#### 11. MCP 与协议设计

##### 你怎么理解 MCP

参考回答：

> 我把 MCP 理解成一层标准化协议，让模型或 Agent 能以统一方式发现并调用外部能力，而不是每接一个工具就写一套私有适配。它的价值主要在标准化接入、能力发现和上下文协作，而不是替代业务本身。

##### MCP 和普通 HTTP API / 函数调用有什么区别

答法：

> 普通 HTTP API 更像面向程序员的接口，调用方通常已经知道地址和参数。MCP 更强调面向 Agent 的能力暴露，除了调用本身，还包含能力描述、资源发现、提示词辅助这类元信息。所以它不只是“再包一层 HTTP”，而是在提高工具接入的一致性和可组合性。

##### 如果把内部能力接成 MCP Server，最核心的收益是什么

回答要点：
- 降低新工具接入成本。
- 降低模型侧和工具侧的耦合。
- 统一鉴权、超时、审计、监控策略。
- 更方便跨团队共享能力。

##### MCP 接入后，如何做认证、鉴权、审计和租户隔离

建议答法：

> 我不会因为用了 MCP 就放松安全要求。能力暴露前仍然要有租户级鉴权、用户级权限校验、操作审计和敏感参数脱敏。高风险工具必须加白名单、人工确认或只允许在受控环境调用。

### 六、模型、Prompt 与效果控制

#### 12. Prompt 编排

##### 你们的系统提示词一般怎么拆

回答要点：
- 全局系统提示词：角色、安全规则、总原则。
- 任务级提示词：当前目标、输入输出要求、业务约束。
- 工具级提示词：何时可调用、参数规则、失败处理。
- 输出约束：JSON schema、字段要求、禁止项。

##### 如何把业务约束、安全规则和输出格式稳定传给模型

参考回答：

> 只靠一段长 prompt 往往不稳定。我倾向于把规则分层：高优先级规则放系统层，任务相关约束放任务层，格式要求尽量用结构化 schema 或后端校验兜底。也就是说，prompt 负责引导，最终稳定性还是靠工程约束保证。

##### 如果模型输出格式不稳定，后端怎么兜底

回答要点：
- 先做 JSON schema 校验。
- 失败时重试并附带纠错提示。
- 仍失败则降级到文本结果或人工介入。
- 对关键链路不要只依赖模型自己“改好格式”。

#### 13. 模型选型与效果评估

##### 为什么选择当前模型？看哪些指标

建议答法：
- 任务效果：正确率、工具调用准确率、结构化输出稳定性。
- 工程指标：时延、成本、并发能力、稳定性。
- 业务指标：用户满意度、自动完成率、人工兜底率。

##### 幻觉、漏答、乱调用工具这几类问题分别怎么治理

参考回答：

> 这几类问题要分开治理。幻觉更依赖检索、工具校验和事实约束；漏答通常要补任务拆解和上下文完整性；乱调用工具则要靠更严格的工具描述、参数校验和调用上限。把所有问题都归咎于“模型不行”是很粗的判断。

##### 成本和效果冲突时，你们怎么做权衡

答法：

> 一般不会全量用最贵模型，而是按任务分层。复杂规划、高价值任务用更强模型，简单分类、格式修复、摘要压缩用更便宜模型。真正有效的是把任务拆分后再做模型路由，而不是所有环节一把梭。

### 七、后端工程化与稳定性

#### 14. 异步任务与可靠性

##### 任务队列是怎么设计的

回答要点：
- 任务入队前先落库，保证可恢复。
- 消费侧按任务类型、优先级、租户做隔离。
- 执行前抢占或加锁，避免重复消费。
- 执行后写回状态和结果摘要。

##### 如何保证任务幂等

参考答法：

> 幂等一般不是靠一个点解决，而是入口幂等键、状态流转校验、外部动作幂等 token 和结果去重一起做。特别是会调用外部系统时，必须假设重试一定会发生，所以要从设计上允许“同一请求多次到达，但副作用只发生一次”。

##### 长任务如何断点续跑

回答要点：
- 每个阶段有明确输入输出和状态。
- 中间结果持久化，不只存在内存。
- 失败后从最后成功阶段恢复。
- 对不可重复副作用步骤加补偿或人工确认。

#### 15. 可观测性与故障排查

##### 你们监控哪些核心指标

建议至少提这些：
- 请求量、成功率、平均时延、P95 / P99。
- 模型调用耗时、失败率、token 消耗、单任务成本。
- 工具调用成功率、超时率、重试率。
- 任务卡住率、死信量、人工介入率。

##### 如果用户说“AI 卡住了”，你第一反应看哪些日志和指标

参考回答：

> 我会先看任务当前状态停在哪个阶段，再顺着 trace 看模型调用、工具调用和队列消费有没有异常。如果状态长时间停留在某一步，就要判断是下游超时、重试打满、状态没回写，还是前端轮询不到。排查时不要先猜模型，先看状态和链路。

##### 如何区分是模型问题、工具问题，还是业务代码问题

回答要点：
- 模型问题：输出不稳定、结构化失败、规划明显偏离。
- 工具问题：超时、鉴权失败、返回脏数据、协议不兼容。
- 业务代码问题：状态没推进、幂等失效、异常未兜底、数据写错。

#### 16. 安全、权限与生产落地

##### 如何避免 prompt injection、越权读数据、误调用危险工具

参考回答：

> 我不会把安全寄希望于“提示词里写一句不要越权”。真正有效的是权限前置校验、工具白名单、输入清洗、敏感操作二次确认、上下文隔离和审计留痕。模型只能做一层意图理解，最终能不能执行高风险动作，必须由后端规则决定。

##### 你觉得 AI 后端和传统后端相比，最大的新增风险是什么

建议答法：

> 我觉得最大的新增风险是系统不再完全确定性。传统后端更多是代码和数据的问题，AI 后端还会引入模型输出不稳定、上下文污染、工具误调用和成本失控这些变量。所以工程治理必须更强，尤其是状态管理、权限控制、观测和回放能力。

### 八、收尾建议

#### 17. 面试时怎么答得更像你真的做过

建议：
- 每个答案尽量带一个真实场景，而不是只讲概念。
- 至少准备 2 个你亲手做过的优化案例。
- 凡是涉及具体数值的题，提前准备真实指标。
- 不确定的框架细节不要编，可以说“我没深度做过，但我会从这几个维度判断”。

#### 18. 哪些地方最容易露怯

风险点：
- 把 Agent 后端说成“就是调模型接口”。
- 只会讲 prompt，不会讲状态机、重试、幂等、审计。
- 只会讲模型能力，不会讲权限、风险和生产稳定性。
- Skill、MCP、记忆这些概念只会背定义，落不到系统设计。

## Go 语言面试题

### 一、切片与数组

#### 切片的 append 问题
```go
func main() {
    s := make([]int, 3, 5)

    appendSlice(s)

    fmt.Println(s)
}

func appendSlice(arr []int) {
    arr = append(arr,888)
}


请问最后输出的是append之后的吗？
```

**答案：**
- 最终输出不是 append 后的结果，而是 `[0 0 0]`。
- 原因：`appendSlice` 里 `arr` 是切片头的拷贝；`append` 后只是修改了函数内的切片长度。外层 `s` 的 `len` 仍然是 3。
- 虽然底层数组第 4 个位置被写入了 `888`（在未扩容前提下），但 `fmt.Println(s)` 只打印前 3 个元素。

正确写法：接收返回值。

```go
func appendSlice(arr []int) []int {
    return append(arr, 888)
}

s = appendSlice(s)
```

#### 1. 切片底层原理与扩容

以下代码的输出是什么？请解释原因。

```go
func main() {
    s := make([]int, 3, 5)
    s[0] = 1
    s[1] = 2
    s[2] = 3

    s = append(s, 4)
    s[0] = 100

    fmt.Println(s)
}
```

追问：
- 切片扩容时新容量的计算规则是什么？
- 扩容后底层数组是原数组的拷贝吗？

**答案：**
- 输出：`[100 2 3 4]`。
- 原因：`len=3, cap=5`，`append(s, 4)` 不会触发扩容，仍使用原底层数组。

追问答案：
- 扩容规则（Go 1.18+ 近似规则）：小切片通常按 2 倍增长；较大切片增长因子变小（约 1.25 倍），并结合内存对齐。
- 触发扩容后会分配新底层数组，并把旧数据拷贝过去。

#### 2. 切片 append 陷阱

请指出下面代码的问题：

```go
func main() {
    s := []int{1, 2, 3}
    s = append(s, 4, 5)

    // 请问 s 和 s[:3] 共享底层数组吗？
    fmt.Println(s[:3])
}
```

**答案：**
- 这段代码本身没有 bug。
- `s` 和 `s[:3]` 一定共享同一个底层数组（`s[:3]` 就是 `s` 的子切片）。
- 常见坑是：如果 append 前后有“旧切片别名”，append 可能扩容，导致别名指向旧数组、`s` 指向新数组。

#### 3. 数组作为函数参数

下面两个函数的区别是什么？

```go
func modifyArray(a [3]int) {
    a[0] = 100
}

func modifySlice(s []int) {
    s[0] = 100
}

func main() {
    arr := [3]int{1, 2, 3}
    slice := []int{1, 2, 3}

    modifyArray(arr)
    modifySlice(slice)

    fmt.Println(arr, slice)
}
```

**答案：**
- 输出：`[1 2 3] [100 2 3]`。
- 数组是值传递，`modifyArray` 改的是副本。
- 切片传的是“切片头副本”，仍指向同一底层数组，改元素会影响外部数据。

#### 4. 切片内存泄漏

以下代码会造成内存泄漏吗？请说明原因。

```go
func main() {
    slice := make([]int, 0, 1000)
    for i := 0; i < 1000; i++ {
        slice = append(slice, i)
    }

    // 只使用前 10 个元素
    process(slice[:10])

    // 请问此时 slice 的底层数组有多大？
    fmt.Println(cap(slice))
}

func process(s []int) {
    // 业务处理
}
```

**答案：**
- `cap(slice)` 是 `1000`。
- 这段代码不一定是“严格内存泄漏”，但有“内存滞留”风险：小切片 `slice[:10]` 仍引用大底层数组。
- 如果这个小切片被长期保存，会导致 1000 容量的大数组不能被 GC 回收。

优化方式：

```go
small := append([]int(nil), slice[:10]...)
process(small)
```

### 二、For 循环与闭包

#### 5. Go for 循环变量捕获

请问下面的代码输出什么？如何修复？

```go
func main() {
    var funcs []func()

    for i := 0; i < 3; i++ {
        funcs = append(funcs, func() {
            fmt.Println(i)
        })
    }

    for _, f := range funcs {
        f()
    }
}
```

追问：
- 这与 Python、JavaScript 的闭包问题有何不同？
- Go 1.22 有什么变化？

**答案：**
- 在 Go 1.21 及之前，常见输出是：

```text
3
3
3
```

- 修复方式：把循环变量作为参数传入闭包，或在循环体内创建新变量。

```go
for i := 0; i < 3; i++ {
    i := i
    funcs = append(funcs, func() { fmt.Println(i) })
}
```

追问答案：
- Python 也有“晚绑定”闭包问题，JS 用 `var` 会踩坑、`let` 可规避。
- Go 1.22 对 `for`/`range` 中由 `:=` 声明的循环变量改为“每次迭代新变量”，这类坑大幅减少，但写参数传递仍是更稳妥习惯。

#### 6. for + goroutine 经典问题

下面代码有什么问题？如何正确修改？

```go
func main() {
    urls := []string{"a.com", "b.com", "c.com"}

    for _, url := range urls {
        go func() {
            fmt.Println(url)
        }()
    }

    time.Sleep(time.Second)
}
```

**答案：**
- 问题 1：旧版本 Go 存在循环变量捕获风险，可能打印重复值。
- 问题 2：`Sleep` 等待 goroutine 不可靠。

推荐写法：

```go
var wg sync.WaitGroup
for _, url := range urls {
    url := url
    wg.Add(1)
    go func(u string) {
        defer wg.Done()
        fmt.Println(u)
    }(url)
}
wg.Wait()
```

### 三、Map 与并发

#### 7. Map 并发读写

下面的代码有什么问题？如何检测和解决？

```go
func main() {
    m := make(map[string]int)

    go func() {
        for {
            m["key"] = 1
        }
    }()

    go func() {
        for {
            _ = m["key"]
        }
    }()

    time.Sleep(time.Second)
}
```

**答案：**
- 问题：`map` 不是并发安全的，会触发数据竞争，甚至 `fatal error: concurrent map read and map write`。
- 检测：`go test -race` 或 `go run -race`。
- 解决：
  - 用 `sync.RWMutex` 保护普通 map。
  - 或用 `sync.Map`（读多写少、键集合动态场景常见）。
  - 或单 goroutine 持有 map，其他协程通过 channel 交互。

#### 8. Map 遍历顺序随机

为什么 Map 的遍历顺序是随机的？这会带来什么问题？如何解决？

```go
func main() {
    m := map[string]int{
        "a": 1,
        "b": 2,
        "c": 3,
    }

    for i := 0; i < 5; i++ {
        for k, v := range m {
            fmt.Println(k, v)
        }
    }
}
```

**答案：**
- Go 规范不保证 map 遍历顺序；运行时会打散迭代起点，避免开发者依赖顺序。
- 问题：测试不稳定、序列化结果不稳定。
- 解决：取出 key 后排序，再按序访问。

#### 9. Map 值类型赋值陷阱

请分析下面代码的问题：

```go
type User struct {
    Name string
    Age  int
}

func main() {
    m := make(map[string]User)

    m["tom"] = User{Name: "Tom", Age: 20}

    user := m["tom"]
    user.Age = 30

    fmt.Println(m["tom"].Age)  // 输出什么？
}
```

**答案：**
- 输出 `20`。
- 原因：`m["tom"]` 取出的是值拷贝，修改 `user` 不会写回 map。
- 修复：

```go
user := m["tom"]
user.Age = 30
m["tom"] = user
```

或直接存指针：`map[string]*User`。

### 四、Defer 与 Panic

#### 10. defer 执行顺序与参数求值

下面代码的输出是什么？

```go
func main() {
    i := 0

    defer fmt.Println("A:", i)
    i++

    defer func() {
        fmt.Println("B:", i)
    }()
    i++

    defer func(i int) {
        fmt.Println("C:", i)
    }(i)
    i++

    panic("error")
}
```

**答案：**
- defer 按 LIFO 执行，输出顺序是：

```text
C: 2
B: 3
A: 0
panic: error
```

- 解释：
  - `A` 在 defer 时就把参数 `i` 计算为 0。
  - `B` 闭包读取执行时的 `i`，为 3。
  - `C` 传参时 `i` 为 2，执行时直接打印该参数。

#### 11. defer 资源泄漏

以下代码会造成资源泄漏吗？

```go
func readFile(path string) ([]byte, error) {
    file, err := os.Open(path)
    if err != nil {
        return nil, err
    }

    defer file.Close()

    return io.ReadAll(file)
}

func process() error {
    file, err := os.Open("/tmp/test.txt")
    if err != nil {
        return err
    }

    // 如果这里 return 了，file 会关闭吗？
    return nil
}
```

**答案：**
- `readFile` 不会泄漏：`defer file.Close()` 在函数返回前执行。
- `process` 会泄漏：打开后没有 `defer file.Close()`，提前 `return` 不会自动关闭。

修复：

```go
func process() error {
    file, err := os.Open("/tmp/test.txt")
    if err != nil {
        return err
    }
    defer file.Close()

    return nil
}
```

### 五、GORM 踩坑

#### 12. GORM 预加载与 N+1 问题

请分析以下代码的 N+1 问题，并给出优化方案：

```go
type User struct {
    ID    uint
    Name  string
    Posts []Post
}

type Post struct {
    ID     uint
    Title  string
    UserID uint
}

func main() {
    var users []User
    db.Find(&users)

    for _, user := range users {
        fmt.Println(user.Name)
        for _, post := range user.Posts {
            fmt.Println(" -", post.Title)
        }
    }
}
```

追问：
- 什么是预加载（Preload）？
- 如何使用 `Join` 优化？
- GORM 的 `Select` 和 `Omit` 有什么用？

**答案：**
- 这段代码 `db.Find(&users)` 默认不会加载 `Posts`，`user.Posts` 为空。
- 常见错误是循环里再查每个用户的 posts，形成 N+1 查询。

推荐：

```go
db.Preload("Posts").Find(&users)
```

追问答案：
- `Preload`：分两条 SQL（主表 + 关联表 `IN (...)`）批量加载关联数据，避免 N+1。
- `Join`：可把数据一次性 JOIN 出来；但一对多会产生主表重复行，通常要配合自定义结构或分组处理。
- `Select` / `Omit`：控制字段列，减少 I/O 与扫描成本，避免不必要字段读写。

#### 13. GORM 事务未生效

以下代码的事务会生效吗？为什么？

```go
func CreateUserAndOrder(db *gorm.DB, user User, order Order) error {
    err := db.Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(&user).Error; err != nil {
            return err
        }

        order.UserID = user.ID
        if err := tx.Create(&order).Error; err != nil {
            return err
        }

        return nil
    })

    return err
}
```

追问：
- GORM 事务回滚后，主键会回滚吗？
- Save 和 Create 有什么区别？

**答案：**
- 会生效。`db.Transaction` 回调返回 error 时自动回滚，返回 nil 时提交。
- 代码本身事务边界正确。

追问答案：
- 主键自增值通常不会因事务回滚而“回退”（取决于数据库实现，MySQL/PostgreSQL常见都不回退序列）。
- `Create`：仅插入新记录。
- `Save`：有主键则更新（通常全字段），无主键则插入；容易误更新零值字段，使用要谨慎。

#### 14. GORM 软删除与查询

用户被软删除后，以下查询还能查到吗？为什么？

```go
type User struct {
    ID   uint
    Name string
    DeletedAt gorm.DeletedAt `gorm:"index"`
}

func main() {

    db.First(&user, 1)  // 能查到已删除的用户吗？

}
```

**答案：**
- `db.First(&user, 1)` 默认查不到已软删除数据，因为自动追加 `deleted_at IS NULL`。
- `db.Unscoped().First(&user, 1)` 能查到（包含软删除数据）。

#### 15. GORM 关联关系更新

如何正确更新 User 和其关联的 Profile？

```go
type User struct {
    ID      uint
    Name    string
    Profile Profile
}

type Profile struct {
    ID     uint
    UserID uint
    Bio    string
}

// 下面的代码能正确更新吗？
func UpdateUser(db *gorm.DB, user User) error {
    return db.Save(&user).Error
}
```

**答案：**
- 仅 `Save(&user)` 不一定按预期更新关联对象，尤其是关联字段的插入/更新策略易与预期不一致。
- 建议显式事务 + 显式更新。

```go
func UpdateUser(db *gorm.DB, user User) error {
    return db.Transaction(func(tx *gorm.DB) error {
        if err := tx.Model(&User{}).
            Where("id = ?", user.ID).
            Updates(map[string]any{"name": user.Name}).Error; err != nil {
            return err
        }

        if err := tx.Model(&Profile{}).
            Where("user_id = ?", user.ID).
            Updates(map[string]any{"bio": user.Profile.Bio}).Error; err != nil {
            return err
        }

        return nil
    })
}
```

### 六、其他经典踩坑

#### 16. Goroutine 泄露

以下代码会造成 goroutine 泄露吗？

```go
func main() {
    ch := make(chan int)

    go func() {
        for i := 0; i < 10; i++ {
            ch <- i
        }
        // 没有关闭 channel
    }()

    time.Sleep(time.Second)
    fmt.Println("done")
}
```

**答案：**
- 会有泄露风险。`ch` 无接收方，发送 goroutine 在第一次 `ch <- i` 就阻塞。
- 在短命 main 程序里进程退出后看起来“结束了”，但在服务型程序会长期堆积。

正确方式：
- 有消费者读取 channel。
- 生产完成后关闭 channel。
- 配合 `context`/`waitgroup` 做生命周期管理。

#### 17. JSON 序列化零值问题

为什么 struct 序列化后某些字段丢失了？

```go
type User struct {
    ID      int    `json:"id"`
    Name    string `json:"name"`
    Age     int    `json:"age,omitempty"`
    Balance int    `json:"-"`
}

func main() {
    user := User{ID: 1, Name: "Tom", Age: 0}
    data, _ := json.Marshal(user)
    fmt.Println(string(data))
}
```

**答案：**
- 输出：`{"id":1,"name":"Tom"}`。
- `omitempty` 会在字段为零值时省略（`Age=0` 被省略）。
- `json:"-"` 表示该字段永远不参与序列化（`Balance` 被忽略）。

#### 18. Context 取消与超时

下面的代码有什么问题？

```go
func main() {
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel()

    go func() {
        time.Sleep(2 * time.Second)
        fmt.Println("goroutine done")
    }()

    select {
    case <-ctx.Done():
        fmt.Println("timeout")
    }
}
```

**答案：**
- 主协程在超时后结束，但子 goroutine 没有监听 `ctx.Done()`，无法被及时取消。
- 在长生命周期服务中会造成失控协程。

修复思路：把 `ctx` 传入 goroutine，并在内部 `select` 监听取消信号。

#### 19. 接口 nil 判断

下面的代码输出什么？

```go
func getError() error {
    var err *MyError = nil
    return err
}

type MyError struct {
    msg string
}

func (e *MyError) Error() string {
    return e.msg
}

func main() {
    err := getError()
    fmt.Println(err == nil)        // 输出什么？
    fmt.Println(err)               // 输出什么？
}
```

**答案：**
- `err == nil` 输出 `false`。
- `fmt.Println(err)` 输出 `<nil>`。
- 原因：接口值由 `(动态类型, 动态值)` 组成。这里动态类型是 `*MyError`（非 nil），动态值是 nil 指针，所以接口本身不为 nil。

常见修复：

```go
func getError() error {
    var err *MyError = nil
    if err == nil {
        return nil
    }
    return err
}
```

#### 20. 切片与数组转换

下面两种方式有什么性能差异？

```go
// 方式1
arr := [3]int{1, 2, 3}
s := arr[:]

// 方式2
s := []int{1, 2, 3}
```

**答案：**
- 方式 1：`arr[:]` 是对已有数组取切片，不复制底层数据。
- 方式 2：直接构造切片字面量，底层数组由编译器决定分配位置（栈/堆），通常也很高效。
- 关键差异不是“绝对快慢”，而是语义：
  - 方式 1 显式复用已有数组。
  - 方式 2 更简洁独立。

#### 24. Gin 路由匹配与参数获取

下面代码的问题是什么？

```go
func main() {
    r := gin.Default()

    r.GET("/user/:name", func(c *gin.Context) {
        name := c.Param("name")
        c.JSON(200, gin.H{"name": name})
    })

    // 请问 /user/ 和 /user/:name 哪个先注册？
    r.GET("/user/", func(c *gin.Context) {
        c.JSON(200, gin.H{"msg": "list"})
    })

    r.Run(":8080")
}
```

追问：
- Gin 的路由是如何匹配的？
- `*` 和 `:` 有什么区别？

**答案：**
- `GET /user/` 走静态路由，`GET /user/tom` 走参数路由。
- 这里不靠“先注册谁”，而是路由树按静态段/参数段规则匹配；静态路由优先级更高。

追问答案：
- `:name`：单段参数，只匹配一个 path segment。
- `*path`：通配剩余路径，通常必须位于路由末尾，可包含 `/`。

#### 25. Gin 中间件执行顺序

以下代码中，MiddlewareA、MiddlewareB、Handler 的执行顺序是什么？

```go
func main() {
    r := gin.New()

    r.Use(MiddlewareA())

    r.GET("/test", MiddlewareB(), func(c *gin.Context) {
        c.JSON(200, gin.H{"msg": "test"})
    })

    r.Run(":8080")
}

func MiddlewareA() gin.HandlerFunc {
    return func(c *gin.Context) {
        fmt.Println("A before")
        c.Next()
        fmt.Println("A after")
    }
}

func MiddlewareB() gin.HandlerFunc {
    return func(c *gin.Context) {
        fmt.Println("B before")
        c.Next()
        fmt.Println("B after")
    }
}
```

**答案：**

```text
A before
B before
Handler
B after
A after
```

- 进入阶段按注册顺序执行；返回阶段按栈回退顺序执行。

#### 26. Gin 上下文并发安全

以下代码有什么问题？

```go
func Handler(c *gin.Context) {
    go func() {
        time.Sleep(time.Second)
        c.JSON(200, gin.H{"msg": "done"})  // 这里有什么问题？
    }()
    c.JSON(200, gin.H{"msg": "ok"})
}
```

**答案：**
- 问题 1：`*gin.Context` 不能在请求结束后被并发写响应。
- 问题 2：同一请求写两次响应，行为未定义/报错风险高。

正确做法：
- 异步任务只做后台处理，不直接写当前响应。
- 如需在 goroutine 读取上下文字段，使用 `c.Copy()`，且只读。

#### 27. Gin 参数绑定与默认值

以下代码能正确获取参数吗？

```go

func main() {
```

追问：

#### 30. 高并发计数器实现

请用 Go 实现一个高性能的计数器，支持：
- Inc() 加一
- Count() 获取当前值
- 1000 个 goroutine 并发调用

你会如何实现？为什么？

**答案：**
- 用 `atomic` 实现无锁计数器，吞吐高、实现简单。

```go
type Counter struct {
    n atomic.Int64
}

func (c *Counter) Inc() {
    c.n.Add(1)
}

func (c *Counter) Count() int64 {
    return c.n.Load()
}

func main() {
    var c Counter
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            c.Inc()
        }()
    }

    wg.Wait()
    fmt.Println(c.Count()) // 1000
}
```

#### 31. 限流器实现

请实现一个令牌桶限流器，要求：
- 每秒生成 N 个令牌
- 桶最多缓存 M 个令牌
- 支持并发安全

**答案：**

```go
type TokenBucket struct {
    mu       sync.Mutex
    tokens   int
    capacity int
    rate     int // 每秒补充 token 数
    ticker   *time.Ticker
    stop     chan struct{}
}

func NewTokenBucket(rate, capacity int) *TokenBucket {
    tb := &TokenBucket{
        tokens:   capacity,
        capacity: capacity,
        rate:     rate,
        ticker:   time.NewTicker(time.Second),
        stop:     make(chan struct{}),
    }

    go func() {
        for {
            select {
            case <-tb.ticker.C:
                tb.mu.Lock()
                tb.tokens += tb.rate
                if tb.tokens > tb.capacity {
                    tb.tokens = tb.capacity
                }
                tb.mu.Unlock()
            case <-tb.stop:
                return
            }
        }
    }()

    return tb
}

func (tb *TokenBucket) Allow() bool {
    tb.mu.Lock()
    defer tb.mu.Unlock()

    if tb.tokens <= 0 {
        return false
    }
    tb.tokens--
    return true
}

func (tb *TokenBucket) Close() {
    close(tb.stop)
    tb.ticker.Stop()
}
```

#### 32. 生产者消费者模型

实现一个生产者-消费者模型：
- 多个生产者并发写入数据
- 多个消费者并发读取数据
- 使用 channel 实现
- 考虑优雅关闭

**答案：**

```go
func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    jobs := make(chan int, 100)

    var producers sync.WaitGroup
    for p := 0; p < 3; p++ {
        producers.Add(1)
        go func(id int) {
            defer producers.Done()
            for i := 0; i < 20; i++ {
                select {
                case <-ctx.Done():
                    return
                case jobs <- i:
                }
            }
        }(p)
    }

    var consumers sync.WaitGroup
    for c := 0; c < 2; c++ {
        consumers.Add(1)
        go func(id int) {
            defer consumers.Done()
            for v := range jobs {
                fmt.Printf("consumer %d got %d\n", id, v)
            }
        }(c)
    }

    producers.Wait()
    close(jobs)      // 生产结束后关闭
    consumers.Wait() // 等消费者自然退出
}
```

### 1. 大屏中包含大量 ECharts 图表或动画，如何避免卡顿？

#### 参考答案
核心思路是“四件事”：按需渲染、减少计算、减少重绘、做好降级。

1. 按需渲染
- 图表进入可视区再初始化（Intersection Observer）。
- 隐藏页签或不可见模块暂停更新。

2. 控制渲染开销
- 关闭或弱化非必要动画：`animation: false` 或缩短动画时长。
- 降低高频交互触发频率（tooltip、mousemove 走节流）。
- 高频更新用 `setOption(option, { notMerge: false, lazyUpdate: true })`，避免整图重建。

3. 数据与线程优化
- 多图共享同一数据拉取结果，统一分发，避免重复请求。
- 复杂聚合放到 Web Worker，避免阻塞主线程。

4. 生命周期与兜底
- 组件卸载时 `chart.dispose()`，避免内存泄漏。
- 建立 FPS 监控，低帧率时自动关闭动画/降采样。

### 2. 大屏数据来自多个接口，如何管理异步请求与失败重试？

#### 参考答案
建议用“数据服务层 + 调度器 + 缓存 + 重试”。

1. 统一数据源配置
```ts
interface DataSource {
  id: string;
  url: string;
  method?: 'GET' | 'POST';
  params?: Record<string, unknown>;
  interval?: number;
  retry?: { max: number; baseDelay: number };
}
```

2. 调度策略
- 启动时注册所有数据源，按 `interval` 轮询或走 WebSocket。
- 相同 `url + params` 短时间内请求合并。
- 成功后统一写入 store，组件只订阅 store。

3. 重试与降级
- 失败按指数退避重试（1s/2s/4s...）。
- 达到上限后保留上次成功数据并展示“数据延迟/异常”状态。
- 用 `AbortController` 取消过期请求，防止脏数据覆盖。

### 7. 说下前端防抖、节流的原理、实现、应用场景

#### 参考答案
1. 原理
- 防抖（debounce）：触发后等待 N ms，N ms 内再次触发就重新计时。
- 节流（throttle）：每 N ms 最多执行一次。

2. 实现
```ts
export function debounce<T extends (...args: any[]) => void>(fn: T, wait = 300) {
  let timer: ReturnType<typeof setTimeout> | null = null;
  return (...args: Parameters<T>) => {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => fn(...args), wait);
  };
}

export function throttle<T extends (...args: any[]) => void>(fn: T, wait = 300) {
  let last = 0;
  return (...args: Parameters<T>) => {
    const now = Date.now();
    if (now - last >= wait) {
      last = now;
      fn(...args);
    }
  };
}
```

3. 场景
- 防抖：搜索输入、窗口 resize、表单校验。
- 节流：滚动监听、拖拽、mousemove、图表 hover 联动。

### 8. 搜索防抖下出现请求乱序（后发先至）怎么办？

#### 参考答案
这是竞态条件（Race Condition）。常见两种解法：

1. AbortController 取消旧请求（推荐）
```ts
let controller: AbortController | null = null;

async function search(keyword: string) {
  if (controller) controller.abort();
  controller = new AbortController();
  const res = await fetch(`/api/search?q=${keyword}`, { signal: controller.signal });
  const data = await res.json();
  renderResults(data);
}
```

2. 版本号兜底
```ts
let version = 0;

async function search(keyword: string) {
  const v = ++version;
  const res = await fetch(`/api/search?q=${keyword}`);
  const data = await res.json();
  if (v === version) renderResults(data);
}
```

## 初中级程序员面试题

### 数据库与数据访问

#### 1. 员工打卡记录表里，怎么找出连续三天都有打卡的员工？

##### 参考答案要点

- 先把打卡时间按天归一，避免同一天多次打卡影响结果：`date(check_time)`。
- 典型做法是先按员工、日期去重，再用窗口函数 `row_number()` 构造连续分组。
- 核心思路：`打卡日期 - row_number()` 相同的记录属于同一段连续日期。
- 再按员工和连续分组聚合，筛出连续天数大于等于 3 的员工。

```sql
WITH base AS (
  SELECT DISTINCT emp_name, DATE(check_time) AS d
  FROM attendance
), grp AS (
  SELECT emp_name,
         d,
         DATE_SUB(d, INTERVAL ROW_NUMBER() OVER (PARTITION BY emp_name ORDER BY d) DAY) AS g
  FROM base
)
SELECT emp_name
FROM grp
GROUP BY emp_name, g
HAVING COUNT(*) >= 3;
```

- 如果面试官追问“没有窗口函数怎么办”，也可以用自连接或变量，但可读性和稳定性通常不如窗口函数。

#### 2. 怎么判断两个 IP 段是否交叉重叠？

##### 参考答案要点（含 IPv4 / IPv6）

1. **先统一模型**
   - 把 IP 段都转成闭区间 `[start, end]`。
   - 同时记录 `ip_version`，`IPv4` 和 `IPv6` 不混比。

2. **核心判定公式**
   - 两个区间 `A=[aStart, aEnd]`、`B=[bStart, bEnd]` 交叉当且仅当：
   - `aStart <= bEnd && bStart <= aEnd`
   - 等价写法：`!(aEnd < bStart || bEnd < aStart)`

3. **IPv4 / IPv6 数值化**
   - `IPv4` 转无符号 32 位整数。
   - `IPv6` 转无符号 128 位，或统一转 16 字节大端序。
   - 不要直接按字符串比较大小。

4. **MySQL 字段类型怎么选**
   - 只存 `IPv4`：可用 `INT UNSIGNED`。
   - 同时支持 `IPv4 / IPv6`：推荐 `BINARY(16)`，再加 `ip_version TINYINT` 区分版本。
   - 如果是 IP 段，就存 `start_ip`、`end_ip` 两个字段。
   - 不建议主存储直接用 `VARCHAR(45)` 做范围比较和索引。
   - 前端展示时，建议后端把二进制或数值 IP 转成字符串返回；除非有导出、人工排查诉求，一般不建议再冗余一份 `VARCHAR` 展示字段。

5. **入参校验**
   - `start <= end`，否则是非法区间。
   - 支持 CIDR 时，先把 `192.168.1.0/24` 这类写法转成 `[start, end]`。

6. **数据库判重 SQL**

```sql
SELECT id
FROM ip_range
WHERE ip_version = :ipVersion
  AND start_num <= :inputEnd
  AND end_num >= :inputStart
LIMIT 1;
```

- 索引建议：`(ip_version, start_num, end_num)`。
- 如果 `IPv6` 用 `BINARY(16)` 按大端序存，也可以按同样逻辑比较。

#### 3. 如何查出“曾命中高危但最终已恢复”的会话？

##### 参考答案要点

- 关键词是“曾命中高危”和“最终已恢复”，说明要看同一会话的状态流转，而不是只看某一条记录。
- 常见做法是先按会话聚合出“是否出现过高危”和“最后状态是什么”。
- 如果有事件时间字段，可用窗口函数先取每个会话最新一条，再和历史高危记录关联。

```sql
WITH latest AS (
  SELECT session_id, status,
         ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY event_time DESC) AS rn
  FROM session_event
), risk AS (
  SELECT DISTINCT session_id
  FROM session_event
  WHERE risk_level = 'HIGH'
)
SELECT l.session_id
FROM latest l
JOIN risk r ON l.session_id = r.session_id
WHERE l.rn = 1
  AND l.status = 'RECOVERED';
```

- 面试里要主动说清：最终状态判断必须基于时间排序，不能直接 `MAX(status)` 这种错误写法。

#### 4. MySQL 全字段加索引会更快吗？

##### 参考答案要点

- 不会。索引不是越多越快，读写收益和维护成本要一起看。
- 写入、更新、删除时，每个索引都要维护，索引越多写放大越严重。
- 索引也占磁盘和内存，可能让缓冲池命中率下降。
- 查询优化器还可能因为候选索引太多而选错计划。
- 正确做法是围绕高频查询、过滤条件、排序条件、覆盖查询来设计索引。

#### 5. MySQL 里，单列索引和联合索引怎么选？

##### 参考答案要点

- 不是“哪个更高级”，而是看查询条件是不是经常一起出现。
- 如果 SQL 常按 `a`、`b` 组合过滤或排序，联合索引通常比给 `a`、`b` 各建一个单列索引更有效。
- 联合索引要注意最左前缀原则，比如 `(a, b, c)` 更容易命中 `a`、`a+b`、`a+b+c`，不一定能高效命中单独的 `b`、`c`。
- 单列索引适合条件相对独立、复用面广的字段；联合索引适合稳定的高频组合查询。
- 索引设计要围绕真实 SQL、过滤条件、排序条件和回表成本，不要只按字段个数机械建索引。

#### 6. MySQL 里，如果 `select *` 查一张一千万行的大表，内存会飙升吗？

##### 参考答案要点

- 不能简单回答“一定会”或“一定不会”，要分数据库端和应用端看。
- MySQL 服务端未必一次把所有结果全塞进内存，但应用如果一次性把结果集全部加载进来，堆内存很容易飙升。
- 风险不只是内存，还包括网络传输、回表、锁持有时间、应用处理耗时。
- 真正的生产建议是分页、流式读取、只查需要字段、限制导出规模。

##### 追问建议（如果面试者只回答"会的"）

> **目标**：区分"背过概念"和"真正理解两端行为"。

1. **先问端**
   "你说的内存飙升，是指 MySQL 服务端，还是应用服务端？"
   → 预期他能说明两端是独立的：MySQL 服务端可以边扫描边发，**不一定**全缓冲在内存；而应用端如果 ORM 一次性把结果集全量塞到 List 里，堆内存才会飙升。

2. **再问服务端机制**
   "MySQL 执行这条语句时，服务端会不会先把一千万行全部缓冲在内存里再发给客户端？"
   → 预期提到 Innodb 可以流式发送，但如果涉及排序、分组、临时表，仍可能需要内部缓冲或落盘。

3. **追问应用端/ORM 行为**
   "那我用 MyBatis 直接返回一个 List，这一千万行对象存在哪里？"
   → 预期说明 JDBC 默认可能一次性拉取，`ResultSet` 被框架映射成一千万个对象后堆内存会直接吃满。

4. **工程解法**
   "生产里真要导一千万行，你怎么做让内存可控？"
   → 预期提到流式/游标读取、分页（注意深分页问题）、只查必要字段、异步任务拆分。

5. **加分追问**
   "如果这条 SQL 还开了一个大事务去执行，除了内存还会带来什么风险？"
   → 预期提到长事务持有锁、undo log 膨胀、阻塞其他 DML，能说到这一步说明真有线上经验。

#### 7. MyBatis 中 `#{}` 和 `${}` 有什么区别？什么时候该用哪个？

##### 参考答案要点

- `#{}` 是预编译参数，占位后由驱动安全绑定，能防 SQL 注入。
- `${}` 是字符串直接拼接，适合表名、排序字段这类不能参数化的位置，但有注入风险。
- 值条件一律优先用 `#{}`。
- 如果不得不用 `${}`，要做白名单校验，例如排序字段只能从固定枚举里选。

#### 8. MyBatis 的一级缓存和二级缓存有什么区别？使用时要注意什么？

##### 参考答案要点

- 一级缓存默认开启，作用域是同一个 `SqlSession`。
- 二级缓存是 Mapper 级别，需要显式开启，并且要考虑数据一致性。
- 一级缓存命中条件比较苛刻：同一会话、相同 SQL、相同参数、期间没有执行更新。
- 二级缓存适合读多写少、更新路径明确的场景；高频变更数据一般不建议强依赖。
- 面试里要讲到缓存失效和脏读风险，否则答案不完整。

#### 9. MyBatis 分页时为什么容易出现 N+1 问题？怎么解决？

##### 参考答案要点

- 分页本身不难，难点在于关联对象装配时容易出现 N+1。
- N+1 本质是先查一页主数据，再按每条记录补查子数据，导致 SQL 数量爆炸。
- 解决思路通常有三类：`JOIN` 一次查、批量 `IN` 回填、明确按需加载。
- 如果用了分页插件，要确认分页发生在真正需要分页的主查询上，而不是错误地作用在关联结果上。

#### 10. MyBatis `ExecutorType.BATCH` 批量写入时，事务边界和回滚怎么设计？

##### 参考答案要点

- `BATCH` 提升的是发送效率，不会自动帮你做好事务设计。
- 事务边界要按业务语义划分，不要为了“更快”把太大批次塞进一个事务里。
- 一般要显式 `flushStatements()` 和 `commit()`，异常时统一回滚。
- 如果批量数据很大，常见做法是按批次分段提交，兼顾回滚成本和锁持有时间。
- 面试里要说明：一旦一批里部分失败，是否允许部分成功，取决于业务要求，而不是框架默认行为。

#### 11. MyBatis 动态 SQL（`<if>/<where>/<trim>/<foreach>`）出现空条件或语义错误，怎么排查？

##### 参考答案要点

- 先打印最终生成的 SQL 和绑定参数，而不是只盯 XML。
- 常见问题有：条件为空导致全表查、`AND/OR` 残留、`IN ()` 空集合、参数名不匹配。
- `<where>`、`<trim>` 就是为了解决多余前缀和分隔符问题，能用就别手写拼接。
- 对更新和删除语句，要加防御性校验，避免空条件直接落到线上。

#### 12. MyBatis-Plus 条件构造器误用导致全表更新/删除，如何防护？

##### 参考答案要点

- 风险点通常不是框架，而是业务代码在条件为空时仍然执行了 `update` 或 `remove`。
- 防护手段：业务层判空、开启 SQL 拦截器、防全表更新插件、关键操作加审批或开关。
- 对动态条件对象，要区分“用户没传”和“传了空值”两种语义。
- 面试里可以补一句：删除或更新前先打印影响条件和 SQL，是非常实际的防线。

#### 13. MyBatis TypeHandler 处理 JSON/枚举映射异常时，如何定位根因？

##### 参考答案要点

- 先确认异常发生在入库、出库，还是中间结果映射阶段。
- 检查数据库字段类型、Java 字段类型、TypeHandler 注册位置是否一致。
- JSON 类型问题常见于序列化器不一致、字段格式不合法、空值处理不统一。
- 枚举问题常见于数据库里存的是 code，但代码按 name 解析，或者新增枚举值未同步。
- 排查顺序通常是：SQL 原始值 -> JDBC 读取值 -> TypeHandler -> 实体字段。

#### 14. MyBatis 插件链（如分页拦截器）顺序不当，为什么会引发 SQL 异常或性能劣化？

##### 参考答案要点

- MyBatis 插件本质是责任链，顺序不同，改写 SQL 的结果就可能不同。
- 如果分页、租户、数据权限、多表改写这类插件顺序不对，可能出现 SQL 语义错误或重复包裹。
- 分页插件如果在错误阶段执行，可能对已经被改写的 SQL 再次加工，导致性能明显变差。
- 排查时要看最终 SQL，而不是只看单个插件的“理论行为”。

### Java 基础与并发

#### 15. 用 `foreach` 遍历集合时直接调用 `remove()` 会报错吗？

##### 参考答案要点

1. **不一定，但绝大多数情况会报错**
   - 通常下一轮到 `iterator.next()` 时，`expectedModCount != modCount`，立刻抛 `ConcurrentModificationException`。
   - **有一个“刚好不报错”的陷阱场景**：如果删除的是倒数第二个元素，当前循环正常结束，但由于内部游标已等于集合大小，迭代器直接判定 `hasNext() == false`，并不会再调用 `next()` 去做 fail-fast 检查，结果“静默成功”但漏掉了最后一个元素。

2. **底层原因与 fail-fast**
   - `foreach` 底层也是迭代器遍历；迭代器维护了 `expectedModCount`，而集合的 `remove()` 会修改 `modCount`。
   - 两者不一致时触发 `ConcurrentModificationException`，这是集合的 fail-fast 机制。
   - fail-fast 是“尽早失败”，属于尽力检测，**不是线程安全保证**，也不保证 100% 每次都抛出异常。

3. **正确做法**
   - 用迭代器自己的 `remove()`。
   - 用 `removeIf()`（Java 8+）。
   - 先收集要删的元素，遍历结束后统一删除。

#### 16. String 处理有哪些常见的性能陷阱？

##### 场景一：`substring` 的内存风险

- Java 6 时代，`substring` 可能共享原字符串底层 `char[]`，小字符串引用会把大数组一起挂住。
- Java 7u6 之后改成复制子串内容，规避了这类内存滞留问题。
- 所以旧版本里，截一小段但长时间持有，可能让大字符串迟迟不能释放。

##### 场景二：敏感词过滤的数据结构选择

- 如果敏感词库很大，不适合反复 `String.replace` 全量扫描。
- 更常见的选择是 Trie 树或 AC 自动机。
- AC 自动机适合多模式匹配，整体效率更稳定。
- `StringBuilder` 适合结果拼装，但不解决“大量词条匹配”的根问题。

#### 17. 为什么有人说 Java 泛型是"伪泛型"？

##### 参考答案要点

- 因为 Java 泛型在编译后会做类型擦除，运行期通常拿不到真实泛型参数。
- `List<String>` 和 `List<Integer>` 运行期大多是同一个原始类型。
- 这也是为什么不能直接 `new T()`、不能创建 `new List<String>[10]`。
- 编译器会补充强转和桥接方法，保证源码层面的类型安全体验。

#### 18. 线程池里的任务越堆越多，你怎么判断问题出在哪？

##### 参考答案要点

- 先区分是“生产太快”还是“消费太慢”。
- 关键观察项：活跃线程数、队列长度、任务平均耗时、拒绝次数、下游 RT、错误率。
- 如果线程都在忙，通常是任务执行慢；如果线程没满但队列长，可能是配置不合理。
- 进一步要看任务是 CPU 密集、IO 阻塞，还是被外部系统卡住。
- 线程池问题很多时候不是线程池本身，而是下游依赖、锁竞争、数据库慢查询导致的连锁反应。

#### 19. HashMap 的扩容机制是怎样的？

##### 参考答案要点

- 底层数组长度通常是 2 的幂。
- 当元素数量超过 `capacity * loadFactor` 时触发扩容，默认负载因子一般是 `0.75`。
- 扩容通常是容量翻倍，然后把旧元素重新分布到新数组里。
- Java 8 里，节点迁移要么留在原索引，要么移动到 `原索引 + oldCap`，比早期版本更高效。

#### 20. 为什么 HashMap 扩容慢？

##### 参考答案要点

- 慢点不在平时 `put`，而在触发扩容时的集中搬迁成本。
- 扩容要申请更大数组，还要重分布原有节点。
- 如果桶里链表或红黑树元素多，迁移成本会更明显。
- 所以业务如果能预估规模，初始化给合理容量通常更稳。

#### 21. 为什么 HashMap 在 Java 7 会出现死循环，而 Java 8 不会？

##### 参考答案要点

- 问题核心是并发扩容，而 `HashMap` 本身又不是线程安全的。
- Java 7 迁移链表时如果多个线程同时 `resize`，链表指针可能被改乱并形成环。
- 一旦成环，后续遍历就可能死循环，CPU 飙高。
- Java 8 调整了迁移实现，降低了成环风险，但不等于并发场景就能安全使用 `HashMap`。
- 正确结论是：并发场景应使用 `ConcurrentHashMap`。

#### 22. HashMap 和 Hashtable 的区别是什么？

##### 参考答案要点

- `HashMap` 线程不安全，`Hashtable` 线程安全，但它通常是整表级同步，性能较差。
- `HashMap` 允许 `null` 键和 `null` 值，`Hashtable` 不允许。
- 现代项目里，并发安全通常优先选 `ConcurrentHashMap`，很少新用 `Hashtable`。

### 后端场景与中间件

#### 23. 如果在一个页面中多次且非常快速的点击保存按钮，如何保证表单只被保存一次？

##### 参考答案要点

- 前端可以先做降噪：点击后按钮置灰、显示 `loading`、避免重复触发。
- 但真正兜底要靠后端幂等：定义稳定的 `Idempotency-Key`，同一业务动作重试时复用。
- 数据库层要有唯一约束，避免并发下“先查后插”失效。
- 常见落地流程：先写幂等记录为 `processing`，首个请求执行业务，成功后写入 `success + 响应快照`，重复请求直接返回快照。
- 面试收尾可以总结：前端防连点只能减压，后端幂等键加唯一约束才是确定性保障。

#### 24. 长连接和长轮询有什么区别？各适用于什么场景？

##### 参考答案要点

- 长连接是一次建立连接后长期复用，例如 TCP 长连接、WebSocket。
- 长轮询是客户端发请求后，服务端先挂住，直到有数据或超时再返回，然后客户端再发下一次请求。
- 长连接更适合高频双向通信，长轮询更像兼容性更好的“准实时”方案。
- 长连接要关注心跳、空闲超时、连接数治理；长轮询要关注请求堆积和超时成本。

#### 25. 怎么保证 MQ 消息不丢失？

##### 参考答案要点

- “不丢失”通常要分生产者、Broker、消费者三段来讲。
- 生产者侧：发送确认、重试、落库消息表或事务消息。
- Broker 侧：持久化、副本机制、刷盘策略。
- 消费者侧：手动 ACK、幂等消费、失败重试、死信队列。
- 面试里最好补一句：真正的目标通常是“可恢复、不重复或可去重”，而不是神话式的绝对零丢失。

#### 26. 缓存设计要注意什么？缓存击穿、穿透、雪崩分别怎么解决？

##### 参考答案要点

- 三大常见问题是：缓存穿透、缓存击穿、缓存雪崩。
- 穿透：查不存在的数据，解决思路是布隆过滤器、空值缓存。
- 击穿：热点 Key 失效瞬间大量请求打到数据库，解决思路是互斥锁、逻辑过期、热点永不过期。
- 雪崩：大量 Key 同时失效，解决思路是过期时间打散、多级缓存、限流降级。
- 设计缓存时还要考虑一致性、预热、淘汰策略和监控。

#### 27. JWT 有哪些常见的安全问题？怎么防护？

##### 参考答案要点

- JWT 适合无状态认证，但不等于“天然安全”。
- 核心风险点有：密钥泄露、过期控制不当、算法配置错误、敏感信息明文放进载荷、令牌被窃取后重放。
- 实践上要做：强密钥、短期有效期、刷新机制、只放必要信息、服务端校验签名和关键声明。
- 如果是高风险系统，还要考虑吊销、黑名单或配合服务端状态管理。

#### 28. JWT 后端是怎么判断 token 正确性的？

##### 参考答案要点

- 先校验签名，确认内容没被篡改且确实是自己信任的签发方发的。
- 再校验标准声明：`exp`、`nbf`、`iat`、`iss`、`aud` 等。
- 然后结合业务校验用户状态、权限版本、是否已注销或被踢下线。
- 签名通过不等于业务一定允许通过，这是面试里很容易漏掉的一点。

#### 29. JWT 是怎么防篡改的？

##### 参考答案要点

- 靠的是数字签名，不是靠 Base64 编码。
- 头和载荷会参与签名计算，服务端收到后用同样算法和密钥重新验签。
- 如果内容被改过，签名校验就过不去。
- 所以 JWT 只能防篡改，不能防“被看到”；载荷默认不是加密的。

#### 30. Nacos 配置动态刷新的原理是什么？实际使用要注意什么？

##### 参考答案要点

- 核心价值是配置变更后应用无需重启即可感知新值。
- 常见前提是使用配置中心托管配置，并配合刷新机制如 `@RefreshScope`。
- 要说明两个边界：
  - 不是所有 Bean 都能无感刷新。
  - 刷新成功不等于业务一定无损，连接池、线程池这类资源型配置要看具体组件是否支持热更新。
- 线上还要关注配置变更审计、灰度发布和回滚。

### Linux 与网络编程

#### 31. Linux 问题合集：怎么查看服务器上某应用的内存占用、应用端口？

##### 参考答案要点

- 看进程：`ps -ef | grep xxx`、`top -Hp <pid>`、`pidstat`。
- 看内存：`top`、`pmap -x <pid>`、`smem`，Java 进程还可结合 `jcmd/jmap`。
- 看端口：`ss -lntp`、`netstat -lntp`、`lsof -i :端口`。
- 面试时最好顺口说明你关注的是 RSS、线程数、监听端口、建立连接数，不只是“会敲命令”。

#### 32. 如果是已经部署在 Linux 服务器上的应用，怎么排查现网错误？

##### 参考答案要点

- 先确认现象：报错范围、开始时间、影响接口、是否可复现。
- 再分层排查：应用日志、进程状态、CPU/内存/磁盘、网络连接、下游依赖。
- 常见顺序是：日志 -> 指标 -> 最近变更 -> 配置差异 -> 下游健康度。
- 如果是 Java 服务，还会看线程栈、GC、连接池、线程池、慢 SQL。
- 面试里强调“先止血再定位”会更像真实线上处理。

#### 33. TCP 三次握手与四次挥手：连接异常怎么定位？

##### 参考答案要点

- 三次握手是为了确认双方收发能力和初始序列号同步，两次不够安全。
- 四次挥手是因为 TCP 支持半关闭，一方不发了不代表另一方也立刻不发。
- `TIME_WAIT` 常见于主动关闭方，`CLOSE_WAIT` 常见于被动关闭方没及时释放连接。
- 常用排查命令：`ss -antp`、`netstat -antp`，重点看各状态数量和趋势。
- 面试往下追时，可以自然切到“`TCP` 和 `UDP` 到底怎么选”，看候选人是否真正理解连接语义和传输模型差异。

#### 34. TCP 与 UDP 选型：聊天、日志上报、实时状态该怎么选？

##### 参考答案要点

- `TCP` 是面向连接、可靠、有序、面向字节流的协议；`UDP` 是无连接、尽力而为、面向数据报的协议。
- 说 `TCP` 面向字节流，意思是它看到的是一串连续字节，不关心你业务上“发了几条消息”；发送端写两次，接收端可能一次读到，也可能分几次读到，所以应用层自己定义消息边界。
- 说 `UDP` 面向数据报，意思是发送方每发一个报文，接收方就是按一个报文一个报文收；不会把两个 UDP 报文自动粘成一个，也不会像 TCP 那样天然出现“半包”语义。
- 但 `UDP` 面向数据报不等于绝对完整可靠，它仍然可能丢包、乱序、重复；如果接收缓冲区太小，还可能把一个报文截断。
- 即时聊天通常选 TCP 或基于 TCP 的 WebSocket，保证有序和可靠。
- 日志上报要看业务容忍度，审计强一致一般选 TCP，允许少量丢失才会考虑 UDP。
- 实时状态上报很多时候更看重“新鲜”，可考虑 UDP 加轻量补偿。
- 不能简单说“UDP 一定更快”，端到端效果还取决于重传、拥塞、链路质量和业务模型。
- 如果候选人已经说到“字节流”和“数据报”，下一步最自然的追问就是第 36 题：为什么 `TCP` 会有粘包半包，而 `UDP` 通常没有这个问题。

#### 35. 粘包与半包：协议边界如何设计？

##### 参考答案要点

- TCP 是字节流，不保证应用层消息边界，粘包和半包不等于 TCP 丢消息。
- 这类问题主要出现在 TCP，不是因为 TCP “有缺陷”，而是因为它本来就只保证字节连续送达，不替应用保留一条条消息的边界。
- UDP 一般不会出现 TCP 这种“半包/粘包”语义，因为它是按数据报收发的；要么收到一个报文，要么丢掉，但不会把两个独立报文自动拼成一个业务消息流。
- 解决办法是应用层 framing，最常见的是“长度字段 + 消息体”。
- 读取循环要维护缓冲区，够一帧就解码，不够就继续读，剩余字节继续留在缓冲区。
- 固定长度、分隔符、长度字段各有场景，但生产里长度字段最常见。
- 如果候选人说到了“长度字段”，就可以继续追问第 43 题：长度字段按什么字节序编码，跨平台时为什么必须统一网络字节序。

#### 36. 高并发 Socket 服务稳定性：如何避免雪崩？

##### 参考答案要点

- 要做连接生命周期治理：空闲超时、读写超时、心跳探活、指数退避重连。
- 要做背压：限制单连接发送队列，慢消费者要降级或断开。
- 要做容量规划：连接数、文件描述符、事件循环线程、端口资源都要有上限。
- 监控要覆盖在线连接数、建连成功率、异常关闭、重连次数、发送队列深度。

#### 37. TCP 滑动窗口是干什么的？零窗口说明了什么？

##### 参考答案要点

- 滑动窗口让发送方不用每发一包都停下来等 ACK，可以连续发送一段数据，提高链路利用率。
- 接收窗口反映对端还能接收多少，拥塞窗口反映当前网络还能承受多少。
- 实际可发送量通常取两者更小值。
- 零窗口通常说明对端应用读慢了，接收缓冲区被打满，不一定是链路断了。

#### 38. TCP 的重传、流量控制、拥塞控制分别在解决什么？

##### 参考答案要点

- 重传解决的是包丢失。
- 流量控制解决的是对端来不及接收。
- 拥塞控制解决的是网络路径承受不住当前发送速率。
- 快重传依赖重复 ACK，比等超时更快；超时重传更保守，但代价更大。

#### 39. UDP 能不能做可靠传输？能的话怎么做？

##### 参考答案要点

- UDP 本身不保证送达、顺序、重传和去重。
- 如果业务需要“基本可靠”，常见做法是加序号、ACK、重传、滑动窗口、去重、必要时加 FEC。
- 但补得越多，就越像自研一个不成熟的 TCP，复杂度会迅速上升。
- 所以生产里一般优先评估成熟协议或现成框架。

#### 40. 为什么 TIME_WAIT 不能随便去掉？太多了怎么办？

##### 参考答案要点

- `TIME_WAIT` 的作用主要是兜住最后 ACK，并隔离旧连接残留报文。
- 它通常出现在主动关闭方，短连接很多时数量高不一定是故障。
- 真正要警惕的是端口耗尽、建连失败率上升、连接风暴。
- 优化优先级通常不是先改内核参数，而是先减少频繁建连、使用连接池和长连接。

#### 41. UDP 的单播、广播、组播，分别适合什么场景？

##### 参考答案要点

- 单播是一对一，最通用。
- 广播是一对整个网段，适合局域网设备发现，但不适合大范围使用。
- 组播是一对多，省带宽，适合同一份数据发给很多接收方。
- 但组播依赖网络设备和路由环境支持，公网环境很多时候不现实。

#### 42. 大端序、小端序与网络字节序：协议字段该怎么解析？

##### 参考答案要点

- 大端序是高位字节放低地址，小端序是低位字节放低地址。
- 网络字节序通常约定为大端，重点不是谁“更先进”，而是跨平台通信必须统一表示。
- 协议里的长度字段、消息类型、序列号这类多字节字段必须明确字节序，不能依赖本机 CPU 内存布局。
- 如果客户端按小端写 `0x00000010`，服务端按大端读，就可能被解析成 `0x10000000`，拆包会直接错位。
- 常见实现方式：Java 用 `ByteBuffer.order(...)`，Go 用 `binary.BigEndian/LittleEndian`，C 用 `htonl/ntohl` 等转换函数。
- 这题很适合作为第 35、36 题之后的实现追问：前面先问协议模型和拆包，后面再问字段到底怎么编码，能更容易区分“会背概念”和“真做过协议”的候选人。

### 前端与 Spring

#### 43. Vue 中 slot 是干什么用的？

##### 参考答案要点

- `slot` 本质是组件的内容占位机制。
- 它解决的是“组件结构固定，但局部内容由外部决定”的问题。
- 常见类型有默认插槽、具名插槽、作用域插槽。
- 作用域插槽的重点是数据在子组件，渲染方式交给父组件。

#### 44. 什么是循环依赖？Spring 是怎么解决循环依赖的？

##### 参考答案要点

- 循环依赖是 A 依赖 B，B 又依赖 A。
- Spring 主要能解决的是单例 Bean 的属性注入循环依赖，不是所有情况都能处理。
- 核心思路是三级缓存，提前暴露早期对象引用，等依赖链走完再完成初始化。
- 构造器循环依赖、原型 Bean 循环依赖通常处理不了。
- 面试里最好补一句：能解决不代表这是好设计，很多时候还是应该拆依赖。

#### 45. 如何理解 Spring Boot 中的 Starter？

##### 参考答案要点

- Starter 可以理解成一组场景化依赖打包。
- 它解决的是依赖组织问题，让你少手动拼装一堆基础组件。
- 真正的自动配置逻辑主要还是在自动配置类里，而不是 Starter 自己完成。
- 一句话总结：Starter 负责把常用依赖带进来，自动配置负责把这些依赖真正用起来。

#### 46. Spring Boot 中为什么不推荐使用 `@Autowired` 注解？

##### 参考答案要点

- 更准确地说，不是不推荐 `@Autowired`，而是不推荐字段注入。
- 字段注入的主要问题是依赖不显式、测试不方便、对象不容易保持不可变。
- 现在更推荐构造器注入。
- 如果类里只有一个构造器，Spring 甚至可以不写 `@Autowired`。

#### 47. Spring Boot 自动配置的实现原理是什么？

##### 参考答案要点

- 自动配置的核心是按条件装配。
- Spring Boot 启动时会加载一批自动配置类，再根据类路径、配置项、已有 Bean 等条件决定是否创建默认 Bean。
- 常见条件注解有 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty`。
- 一句话总结：依赖在、条件满足、你又没自己定义，Spring Boot 就帮你把默认配置装起来。

### 数据库深度与 Java 进阶

#### 48. MySQL `EXPLAIN` 里的 `type` 怎么判断执行计划是否可接受？

##### 参考答案要点

- `type` 从优到劣常见有：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。
- 日常最关注的几类：
  - `ref` / `range`：说明用到了索引且效率不错，通常是可接受的。
  - `index`：全索引扫描，比全表好但在大数据量时仍可能慢。
  - `ALL`：全表扫描，一般要避免，尤其是大表上的高频查询。
- 判断执行计划不能只看 `type`，还要结合：
  - `key`：实际使用的索引。
  - `rows`：预估扫描行数，越小越好。
  - `Extra`：出现 `Using filesort` 或 `Using temporary` 时要警惕，排序/分组没走索引可能带来额外开销。
- 初中级标准答案里不要机械追求 `const`，而是要说明“核心链路尽量 `ref` 以上，明显出现 `ALL` 且 `rows` 很大时要优化”。

#### 49. MySQL 主从延迟怎么排查？`binlog` 三种格式在一致性上有什么区别？

##### 参考答案要点

**排查思路**
- 先看 `SHOW SLAVE STATUS` 里的 `Seconds_Behind_Master`，它只能做粗略参考。
- 更准确的对比是看 `Master_Log_File` / `Read_Master_Log_Pos`（IO线程）和 `Relay_Master_Log_File` / `Exec_Master_Log_Pos`（SQL线程）的位点差。
- 常见根因：从库有大事务、慢 SQL、DDL 锁表、从库硬件差、单线程 SQL 回放瓶颈。
- 如果开了并行复制，还要看 worker 线程有没有等待或冲突。

**binlog 格式**
- `STATEMENT`：记录原始 SQL，日志量小，但某些非确定性函数（如 `UUID()`、`NOW()`）可能导致主从数据不一致。
- `ROW`：记录每行实际变更，日志量大，主从一致性最强，是最推荐的生产格式。
- `MIXED`：MySQL 自己判断，安全语句用 `STATEMENT`，不安全时用 `ROW`，折中方案。
- 一致性排序：`ROW` > `MIXED` > `STATEMENT`。

#### 50. Java 8 的 `CompletableFuture` 相比原生 `Future` 解决了什么痛点？实际使用时怎么防止回调地狱和异常吞没？

##### 参考答案要点

- `Future` 的痛点：
  - `get()` 阻塞，不能方便地链式组合多个异步任务。
  - 缺少内置的异常处理和任务编排能力（如“等两个都完成再合并结果”）。
- `CompletableFuture` 的改进：
  - 支持链式调用：`thenApply` / `thenAccept` / `thenCompose`。
  - 支持组合：`thenCombine`、`allOf`、`anyOf`。
  - 支持显式完成和异常处理：`complete`、`exceptionally`、`handle`。

**防止回调地狱**
- 避免嵌套 `thenAccept`，改用 `thenCompose` 做扁平化链式调用。
- 把每个阶段拆成语义清晰的小方法，而不是把所有逻辑堆在一个 lambda 里。

**防止异常吞没**
- 链里至少留一个 `exceptionally` 或 `handle` 做兜底，否则未捕获异常可能被静默吞掉。
- 如果最终要同步拿到结果，用 `get(timeout, TimeUnit)` 或 `join()`，不要无限等待。
- 注意默认异步执行走的是 `ForkJoinPool.commonPool()`，任务量大时容易饱和；对核心链路建议传入自定义线程池。

### 容器、中间件与 Java 并发

#### 51. `Dockerfile` 里的 `CMD` 和 `ENTRYPOINT` 有什么区别？生产镜像怎么分层优化减小体积？

##### 参考答案要点

**`CMD` vs `ENTRYPOINT`**
- `ENTRYPOINT`：容器启动的固定入口命令，不容易被直接覆盖（除非显式 `--entrypoint`）。适合把容器当成一个“可执行文件”来用。
- `CMD`：为 `ENTRYPOINT` 提供默认参数，或单独作为默认执行命令。如果用户 `docker run` 时带了命令行参数，会直接覆盖 `CMD`。
- 常见组合：用 `ENTRYPOINT` 写主程序路径，`CMD` 写默认参数，兼顾“开箱即用”和“灵活覆盖”。

**镜像分层优化**
- 层缓存：Docker 每一层被构建后只要该层指令输入不变，就能复用。把变动最小的指令放在前面，变动大的放在后面。
- 减少层数：能用一条 `RUN` 完成的操作尽量合并（如先 `apt-get update` 再 `install` 然后清理缓存），避免残留临时文件。
- 使用更小的基础镜像：生产环境尽量不用 `ubuntu:latest`，优先 `alpine`、`distroless` 或者 `jlink` 裁剪后的 JDK 基础镜像。
- 多阶段构建：把编译、打包和运行拆成不同阶段，最终镜像只保留产物和运行时，不带编译工具、源码和依赖缓存。

#### 52. Nginx 反向代理时，502 Bad Gateway 和 504 Gateway Time-out 排查思路有什么区别？

##### 参考答案要点

**502 Bad Gateway**
- 含义：Nginx 作为网关，成功连到了上游，但上游返回了**不合法或无法处理**的响应。
- 典型根因：
  - 上游服务崩溃、进程退出、端口未监听。
  - 上游主动断开连接（如 PHP-FPM 子进程异常终止）。
  - 响应头过大，超过 Nginx `proxy_buffer_size`。
- 排查方向：直接访问上游地址看是否正常；看上游应用日志是否有异常；检查 Nginx `error.log` 里的 `upstream prematurely closed connection` 等关键字。

**504 Gateway Time-out**
- 含义：Nginx 在规定时间里**没等到上游的完整响应**。
- 典型根因：
  - 上游处理太慢（大事务、慢 SQL、死循环）。
  - 上游服务本身有健康，但网络丢包或延迟高。
  - Nginx 的 `proxy_read_timeout`、`fastcgi_read_timeout` 设置过短。
- 排查方向：压测/直接请求上游接口看 RT；检查上游 CPU/线程池/连接池是否被打满；逐步放大 Nginx 超时时间看是否只是配置问题。

**核心区别**
- 502 是“连上了但上游给了坏结果”，重点看**上游是否正常活着**。
- 504 是“等太久了没结果”，重点看**上游处理耗时和网络/超时配置**。

#### 53. `ThreadLocal` 的实现原理是什么？为什么在线程池场景下特别容易发生内存泄漏？应该怎么正确使用？

##### 参考答案要点

**实现原理**
- 每个 `Thread` 对象内部维护了一个 `ThreadLocalMap`，key 是 `ThreadLocal` 的弱引用，value 是用户实际存储的对象。
- `ThreadLocal.set()` 时其实是往当前线程的 `ThreadLocalMap` 里写入键值对。
- 取数据时也从当前线程自己的 Map 里根据 `ThreadLocal` 实例查找，所以不同线程之间天然隔离。

**线程池下为什么容易内存泄漏**
- 线程池里的线程是复用的，不会随着任务结束而销毁。
- 如果用了 `ThreadLocal` 但没有 `remove()`，线程归还线程池后，`ThreadLocalMap` 里的 Entry 还会跟着这条线程一直存在。
- 虽然 `ThreadLocal` 的 key 是弱引用，会在 GC 时被回收，但 value 是强引用；如果 key 变成 null 而 value 没被清理，就会形成**无法访问但无法释放**的泄漏点。

**正确使用方式**
- 用完即清：在 `finally` 块里调用 `threadLocal.remove()`，确保无论业务是否异常都清理。
- 避免大对象长期存放：不要把整个请求上下文或超大对象长期塞在 `ThreadLocal` 里。
- 如果是 Tomcat/Jetty 等带线程池的 Web 容器，更要注意拦截器或过滤器里 `remove()` 的兜底。
- 面试里能说出 `ThreadLocalMap` + 弱引用 key + 强引用 value 的组合，才算真正理解泄漏根因。

### 容器、Java 基础与工程选型

#### 54. Docker 容器的网络模式有什么区别？bridge 模式下同宿主机容器偶尔互通不通，怎么排查？

##### 参考答案要点

**四种常见网络模式**
- `bridge`：默认模式，Docker 为容器创建独立的 veth 接口并桥接到宿主机的 `docker0`，容器通过 NAT 访问外部网络。是最常见的隔离方案。
- `host`：容器直接使用宿主机的网络栈，没有独立的 IP，端口与宿主机共享。性能最好但隔离性最差。
- `none`：关闭容器网卡，只有 loopback，适合对网络要求极高的隔离场景。
- `container`：新容器共享另一个指定容器的网络命名空间，常见于 sidecar 模式（如日志采集、服务网格代理）。

**bridge 模式下同宿主机容器偶尔不通的排查**
- 先看容器是不是在同一自定义 bridge 网络里。默认 `bridge` 不支持通过容器名 DNS 解析，跨 compose 或手动启动时容易连到不同网桥。
- 检查 `iptables` / `firewalld` 是否拦截了网桥间流量，尤其是 CentOS 类系统默认策略较严。
- 看 Docker 的 `userland-proxy` 是否导致端口冲突或回环异常。
- 验证方法：
  - `docker network inspect <network>` 确认容器 IP 和子网。
  - 在容器里 `ping` / `curl` 对端 IP，排除 DNS 问题。
  - 宿主机抓包 `tcpdump -i docker0` 看包是否走到网桥。
- 能用自定义 bridge 尽量不用默认 bridge，自定义网络自带 DNS 和更好的隔离性。

#### 55. 什么是 Java 中的 SPI 机制？JDBC、SLF4J 是怎么利用 SPI 的？和 Spring Boot 自动配置有什么关系？

##### 参考答案要点

**SPI 概念**
- SPI（Service Provider Interface）是 JDK 提供的一套服务发现机制，核心思想是“接口由上层定义，实现由下层扩展”，通过约定好的配置文件在运行期加载具体实现。
- 配置文件路径：`META-INF/services/接口全限定名`，文件内容是实现类的全限定名。
- 加载器：`ServiceLoader.load(Interface.class)`，在运行期读取配置文件并通过反射实例化实现类。

**JDBC 的例子**
- `java.sql.Driver` 是标准接口，各数据库厂商提供自己的实现（如 `com.mysql.cj.jdbc.Driver`）。
- JDBC 4.0 之后，驱动 jar 包里只要带了 `META-INF/services/java.sql.Driver`，`DriverManager` 就能自动发现，不需要再手动 `Class.forName()`。

**SLF4J 的例子**
- SLF4J 定义了日志门面接口，logback、log4j2 等实现jar通过 SPI 把自己注册进去，应用层只依赖门面，不直接依赖具体实现。

**与 Spring Boot 自动配置的关系**
- Spring Boot 的自动配置沿用了类似的“约定大于配置”思想，但它的加载机制不是 JDK SPI，而是基于 `spring.factories`（Spring Boot 2.7+ 开始推荐 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）。
- 面试官如果问“是不是 SPI”，要区分清楚：思想上类似，技术实现上 Spring Boot 有自己的加载器，不要混为一谈。

#### 56. `ArrayList` 和 `LinkedList` 在时间复杂度上的差异大家都知道，那在实际工程里，除了遍历和随机访问，还有什么因素会影响你选哪个？

##### 参考答案要点

**时间复杂度是基础，不是全部。** 工程选型还要看下面几个维度：

1. **CPU 缓存友好性（Cache Locality）**
   - `ArrayList` 底层是连续数组，元素在内存中紧凑排布，CPU 预取命中率高，顺序遍历非常快。
   - `LinkedList` 节点分散在堆上，每个节点都要解引用指针，Cache Miss 严重，即使理论上 `get()` 是 O(n) 对 O(n)，实际遍历 `LinkedList` 往往比 `ArrayList` 慢一个数量级。

2. **内存占用与 GC 压力**
   - `ArrayList` 只存对象引用，额外开销小（当然数组本身可能有扩容冗余）。
   - `LinkedList` 每个节点都要维护 `prev` / `next` 两个指针，对象头开销大；节点数多时堆内存和 GC 遍历成本显著上升。

3. **随机插入删除的“理论”与“现实”**
   - 虽然 `LinkedList` 随机插入是 O(1)，但前提是已经定位到节点。如果通过索引插入，需要先 O(n) 遍历找到位置，整体并不快。
   - 真正适合 `LinkedList` 的场景是：频繁在头尾插入/删除，或者需要利用它实现队列/双端队列，且数据量不大。

4. **工程结论**
   - 现代 Java 工程里，绝大部分场景默认选 `ArrayList`；除非明确需要双端队列语义，或者频繁头尾操作，否则不推荐 `LinkedList`。
   - 面试时能说清“Cache Locality 和 GC 压力”比只会背 O(1)/O(n) 更能体现工程思维。

### 高频业务场景与根因追问

#### 57. 抽奖系统用 Redis + Lua 扣库存，为什么能保证并发下的正确性？

##### 参考答案要点

**1. Redis 单线程执行模型是前提**
- Redis 服务端处理命令是**单线程串行执行**的（Redis 6.0+ 多 IO 线程仅负责网络读写，命令执行仍是单线程）。
- 这意味着任一时刻不会有两个客户端命令同时修改同一份数据，天然避免了线程竞态。

**2. Lua 脚本在 Redis 里具备原子性**
- Lua 脚本被发送到 Redis 后，会被当作一个**不可分割的执行单元**。
- 执行期间不会插入任何其他客户端命令，直到脚本全部执行完毕。
- 所以 `判断库存 > 0 → 扣减库存 → 记录日志` 在 Redis 视角里是一步完成的，中间不存在被其他请求打断的窗口。

**3. 为什么普通命令序列不行？**
- `GET stock` → 应用层判断 → 再发 `DECR`，这是**三个独立的网络往返**。
- `GET` 和 `DECR` 之间，其他客户端可能已经把库存扣光，导致超卖。

**4. 为什么不推荐 `WATCH` + `MULTI`/`EXEC`？**
- `WATCH` 是乐观锁，高并发写冲突下会频繁失败重试，吞吐量急剧下降。
- Lua 脚本是**一次执行、没有重试风暴**。

**5. 这个方案的风险和边界**
- **阻塞主线程**：Lua 不能写太重，大量循环会阻塞整个 Redis 实例。
- **集群限制**：Redis Cluster 要求 Lua 访问的所有 key 在同一 slot，否则报错。通常用 hash tag（如 `{lottery}:stock`）强制同 slot。
- **持久化一致性**：Redis 扣减成功仅代表内存数据变了，如果此时宕机且没来得及落盘/同步从库，重启后库存可能回退。核心业务一般要配合 MySQL 最终一致性或对账兜底。

##### 追问建议

1. **"把 Lua 脚本换成在客户端用 Shell 脚本执行同一组 Redis 命令，能不能保证同样的正确性？"**
   → **不能**。Shell 脚本在客户端执行时，发出去的仍是多条独立网络请求，Redis 服务端会把它们当成多个独立命令依次处理，完全可能被其他客户端命令穿插，原子性被破坏。

2. **"Redis 扣减成功，但后面异步写数据库时失败了，库存已经少了但实际没发奖，怎么兜底？"**
   → 预期提到：**异步对账、定时扫描差异、预扣库存超时回滚、补偿机制**等。

## 高级社招程序员面试

### 1. 资源隔离怎么做？

参考答法：
- 资源隔离通常分为计算、内存、网络、存储、线程池和租户维度几个层面。
- 单机层面可以依赖容器或进程级隔离，比如 CPU 配额、内存限制、文件句柄、磁盘配额。
- 应用层还要做线程池隔离、连接池隔离、队列隔离，避免一个慢业务拖垮全局。
- 如果是多租户系统，通常还要做租户级限流、配额和数据隔离，防止热点租户挤占公共资源。
- 面试里最好补一句：资源隔离不是目的，核心是把故障域缩小，让单点问题不会扩散成整体雪崩。

### 2. 性能优化怎么做？

参考答法：
- 先量化再优化，不要上来就改代码。先看接口 RT、吞吐、CPU、内存、GC、SQL、缓存命中率。
- 再按链路拆分瓶颈：是计算慢、IO 慢、锁竞争、数据库慢，还是网络抖动。
- 常见手段包括：缓存、异步化、批处理、索引优化、对象复用、减少序列化、连接池调优、热点隔离。
- 优化完成后要做压测和回归，验证收益与副作用，比如命中率提升了多少、时延下降了多少、峰值下是否稳定。
- 高级岗位回答里最好体现方法论：监控定位、假设验证、最小改动、灰度发布、持续观测。

### 3. 讲讲 Socket 编程。

参考答法：
- Socket 编程本质上是基于传输层协议建立进程间通信，最常见的是 TCP 和 UDP。
- TCP 场景下，服务端一般是 bind、listen、accept，客户端 connect，建立连接后再收发数据。
- 真正工程里重点不是 API，而是连接生命周期、心跳保活、超时控制、半包粘包处理、背压和异常重连。
- 高并发服务通常不会一连接一线程，而是基于 IO 多路复用或 Netty 这类事件驱动框架处理。
- 如果你做过项目，可以补充实际问题，比如连接数过多、发送缓冲区堆积、空闲连接清理、协议解析失败等。

### 4. 粘包、拆包怎么处理？

参考答法：
- TCP 是字节流，没有消息边界，所以应用层必须自己定义协议边界。
- 常见做法有三种：固定长度、分隔符、长度字段加消息体，其中最常见的是长度字段协议。
- 发送端可能把多条消息合并发送，接收端也可能一次只收到半条，因此必须有累积缓冲区。
- 解码时先判断缓冲区里是否拿到了完整包头，再根据长度字段判断消息体是否完整，不完整就继续读。
- 实战里还要做非法包长度校验，避免因为脏数据或恶意流量导致内存被打爆。

### 5. MySQL 开窗函数怎么用？

参考答法：
- 开窗函数适合“保留明细行，同时做组内排名、累计、对比上一行下一行”这类场景。
- 常见函数有 `row_number()`、`rank()`、`dense_rank()`、`sum() over (...)`、`lag()`、`lead()`。
- 典型用法比如：找每个用户最新一条记录、查连续打卡、做分组 TopN、算累计金额。
- 面试里要说明 `partition by` 是分组范围，`order by` 是窗口内排序规则。
- 还要补一句：开窗函数可读性强，但大数据量下仍要关注排序和临时表开销，必要时配合索引和执行计划分析。

### 6. 怎么实现断点续传？

参考答法：
- 核心思想是把大文件拆成多个分片，每个分片独立上传，并在服务端记录上传状态。
- 客户端首次上传前先拿上传任务 ID，之后按分片序号上传；失败重试时只补未完成分片。
- 服务端一般要记录文件标识、分片总数、已完成分片、校验值和最终合并状态。
- 全部分片上传完成后触发合并，再做完整性校验，比如文件大小、MD5 或分片校验和。
- 生产里还要考虑并发重复上传、过期分片清理、秒传判重、MinIO 或对象存储的残余碎片清理。

### 7. Java 方法传参是值传递还是引用传递？

参考答法：
- Java 永远只有值传递。
- 基本类型传的是值本身；对象传的是“引用变量里保存的地址值”的副本。
- 所以很多人误以为对象是引用传递，本质上仍然是值传递，只是这个值恰好是地址。

### 8. 如果把一个对象传进方法，在方法里修改对象属性，外面的对象会不会变？

参考答法：
- 会变。
- 因为方法参数和外部变量虽然是两个不同引用变量，但它们指向同一个对象实例。
- 在方法里改的是对象内部状态，不是把外部引用重新绑定，所以调用方能看到修改结果。

### 9. 如果在方法里重新 new 一个对象赋给参数，外面的对象会不会变？

参考答法：
- 不会变。
- 因为你只是让方法内部那个参数引用指向了新对象，外部引用仍然指向原来的对象。
- 这正好说明 Java 传参不是引用传递，否则外部引用会一起被改掉。
