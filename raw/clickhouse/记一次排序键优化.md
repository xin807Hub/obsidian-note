# 记一次排序键优化

这篇文档记录一次 ClickHouse 排序键调整，同时补充更重要的部分：排序键优化的使用边界，什么情况适用，什么情况不适用，以及实际设计时应该怎么判断。

## 背景

业务表 `TK_DB_SP.ods_traffic_records_local` 使用 `MergeTree`，分区键为：

```sql
PARTITION BY toYYYYMMDD(start_time)
```

原始主键和排序键如下：

```sql
PRIMARY KEY (
    start_time,
    msisdn,
    imsi,
    imei,
    src_ip,
    session_id,
    app_type,
    app_id,
    app_detail_id
)
ORDER BY (
    start_time,
    msisdn,
    imsi,
    imei,
    src_ip,
    session_id,
    app_type,
    app_id,
    app_detail_id,
    log_time
)
```

优化后改为：

```sql
PRIMARY KEY (
    toStartOfHour(start_time),
    msisdn,
    imsi,
    imei,
    src_ip,
    session_id,
    app_type,
    app_id,
    app_detail_id
)
ORDER BY (
    toStartOfHour(start_time),
    msisdn,
    imsi,
    imei,
    src_ip,
    session_id,
    app_type,
    app_id,
    app_detail_id,
    toStartOfHour(log_time)
)
```

这次调整最关键的点，不是“字段变少了”或者“写法变了”，而是把高精度时间列从原始时间戳改成了小时粒度，使排序键更贴近实际查询粒度。

## 结论先行

排序键优化是 ClickHouse 最有效的性能手段之一，但绝不是通用模板。

它适合：

- 查询模式稳定，过滤路径相对固定。
- 慢查询主要问题是扫描行数太多。
- 业务经常按某个时间粒度查询，原始时间精度过细。
- 常用过滤字段能形成明确的排序键前缀。

它不适合：

- 查询模式非常发散，没有主路径。
- 想靠一个排序键照顾所有字段的任意组合查询。
- 读并不是瓶颈，真正瓶颈是写入、merge、join 或复杂聚合。
- 无法接受重建表和回灌历史数据的改造成本。

我的建议是：

- 大部分场景都应该参考排序键设计思路。
- 但大部分场景都不应该直接照抄某一份排序键定义。

应该参考的是方法，而不是答案本身。

## 排序键到底在优化什么

`MergeTree` 的核心不是逐行索引，而是稀疏主键索引。数据按 `ORDER BY` 的顺序存放，ClickHouse 在读取时会根据主键索引判断哪些 granule 需要读，哪些可以跳过。

所以排序键优化，本质上是在优化两件事：

1. 让常用过滤条件对应的数据在物理上更集中。
2. 让查询在读取前就能裁掉更多无关数据。

这意味着排序键最擅长的是减少扫描，不是万能加速器。它通常不能直接解决这些问题：

- 大量 CPU 花在复杂表达式计算上。
- 大表 join 本身代价很高。
- 聚合基数极大。
- SQL 根本没有利用到排序键前缀。

## 这次案例为什么有效

原表把两个高精度时间列直接放进排序路径：

```sql
start_time DateTime64(6)
log_time   DateTime64(3)
```

高精度时间列有一个典型问题：基数很高、重复值少、局部性差。如果业务查询其实更偏向“按小时分析”，那么微秒级或毫秒级精度对排序裁剪帮助并不大，反而会把数据打散。

改成 `toStartOfHour(...)` 后，收益通常来自：

- 同一小时内的数据更容易聚集。
- 主键索引的范围裁剪更稳定。
- 读取 granule 数量下降。
- 查询的 `read_rows` 和 `read_bytes` 更容易下降。

所以这个案例的关键不是“时间字段放前面”，而是“时间字段的粒度和查询粒度对齐”。

## 什么情况适用

### 1. 查询模式稳定

如果大部分查询都长这样：

```sql
WHERE start_time >= ...
  AND start_time < ...
  AND msisdn = ...
```

或者：

```sql
WHERE toStartOfHour(start_time) = ...
  AND imsi = ...
  AND app_type = ...
```

说明查询路径相对固定，这时围绕它设计排序键，通常收益明显。

### 2. 主过滤路径具备明显前缀

如果查询常常是“先时间、再用户标识、再业务分类”这种路径，那么排序键就适合按类似顺序组织，因为前几个字段就能显著缩小扫描范围。

### 3. 慢在扫描，不是慢在算

如果慢查询的典型特征是：

- `read_rows` 很大
- `read_bytes` 很大
- 结果集很小

那么说明主要问题是裁剪不够，排序键优化优先级就很高。

### 4. 常用字段精度过细

这个案例最典型。如果业务按小时查，但排序键用的是 `DateTime64(6)`，通常就存在明显优化空间。

常见可考虑粗化的形式：

- `toStartOfMinute`
- `toStartOfHour`
- `toDate`

前提是业务确实按这个粒度查询，而不是仍然依赖秒级甚至毫秒级顺序。

### 5. 大表、小结果集

对十亿级、百亿级明细表，如果查询只命中极小子集，那么排序键设计往往非常关键。扫描少 10 倍和少 100 倍，实际延迟会完全不同。

## 什么情况不适用

### 1. 查询模式非常发散

如果线上查询今天按 `src_ip`，明天按 `cell_id`，后天按 `device_id`，而且都很重要，那么不存在一个排序键能同时服务所有路径。

这类场景更应该优先考虑：

- 专题表拆分
- 物化视图
- 跳数索引
- 布隆过滤索引
- 预聚合

### 2. 查询根本不命中排序键前缀

例如排序键是：

```sql
ORDER BY (toStartOfHour(start_time), msisdn, imsi, imei, ...)
```

但查询大量是：

```sql
WHERE device_id = 'xxx'
```

这时即使 `device_id` 也存在于表中，排序键也帮不上太多，因为查询没有利用到前缀裁剪。

一个常见误区是：`ORDER BY` 里有这个字段，所以查这个字段一定快。实际不是，关键看它是否处于能被有效裁剪的前缀路径中。

### 3. 写入吞吐是首要目标

排序键越复杂：

- 写入排序成本越高
- part merge 成本越高
- 主键索引越重
- 内存占用可能更高

如果业务是高吞吐写入、查询要求一般，那么过度优化排序键可能得不偿失。

### 4. 试图把排序键当成万能索引

排序键不能替代：

- SQL 本身优化
- 分区策略设计
- 预聚合
- 物化视图
- 跳数索引

如果慢查询本质是全表聚合、join 爆炸、表达式开销高，改排序键收益通常有限。

### 5. 改造成本无法接受

调整 `ORDER BY` 往往意味着：

- 新建表
- 回灌数据
- 验证数据一致性
- 切流量

所以收益不明确时，不能直接在生产全量表上冒险，应先做影子表验证。

## 排序键设计时怎么判断值不值得改

### 1. 先看查询日志

先从 `system.query_log` 找出真正的高频和高成本 SQL：

```sql
select *
from system.query_log
where event_date >= today();
```

重点看：

- 哪些 SQL 最慢
- 哪些 SQL 最频繁
- 哪些 SQL 读取行数最多
- 过滤条件最稳定的是哪些字段

如果高频 SQL 根本没有稳定模式，就不要急着改排序键。

### 2. 看读放大

重点关注这些指标：

- `read_rows`
- `read_bytes`
- `result_rows`
- `query_duration_ms`

如果 `read_rows` 远大于 `result_rows`，说明扫描裁剪不理想，排序键就值得重点评估。

### 3. 看过滤字段能否形成稳定前缀

一个好的排序键，不是字段越多越好，而是前几个字段就能明显缩小范围。

通常更适合靠前的字段：

- 高频时间范围字段
- 高频等值过滤字段
- 能提升局部聚集性的字段

通常不适合过早放前面的字段：

- 很少参与过滤的字段
- 高基数且随机分布的字段
- 只用于展示或回传的字段

### 4. 看字段粒度是不是过细

这些字段经常要谨慎处理：

- `DateTime64(6)`
- UUID
- 高随机字符串 ID

它们不一定不能放进排序键，但通常不适合直接放在前部，除非查询模式高度依赖它们。

## 一套更实用的设计原则

### 原则 1：排序键只服务主查询路径

不要企图用一个排序键覆盖所有查询。排序键服务的是主路径，不是所有路径。

### 原则 2：优先考虑聚集性，不是业务重要性

某个字段业务上很重要，不代表它适合放在排序键前面。能不能让数据更聚集，才是关键。

### 原则 3：时间字段经常应该入排序键，但不一定保留原始精度

日志、流水、明细类表里，时间字段通常都很重要，但应根据查询粒度决定是否做粗化。

### 原则 4：排序键不要无止境变长

排序键过长会带来额外比较成本、索引成本和 merge 成本。只保留真正能帮助裁剪的字段。

### 原则 5：分区键和排序键要配合

分区解决粗裁剪，排序键解决分区内细裁剪。两者应该协同设计，而不是重复堆叠。

## 这次案例的使用边界

这次把 `start_time` 和 `log_time` 从原始高精度时间改成小时粒度，我认为成立的前提大致是：

- 大部分查询都带时间范围。
- 时间分析粒度更接近小时，而不是秒级或毫秒级。
- `msisdn / imsi / imei / src_ip / session_id` 是高频过滤字段。
- 主要瓶颈是扫描过多，而不是聚合或 join。

如果这些前提不成立，这个方案就未必值得照搬。

例如下面几种情况就要重新评估：

- 查询经常要求更细时间顺序。
- 高频查询并不依赖 `msisdn/imsi/imei`，而是依赖 `device_id` 或 `cell_id`。
- 业务更关注写入吞吐，不愿承担更复杂排序带来的额外成本。

## 副作用和风险

### 1. 重建成本高

历史大表调整排序键，通常不是小修小补，而是一次结构性改造。

### 2. 某些查询可能变差

优化一定是有取舍的。主路径变快，不代表所有查询都变快。

### 3. merge 和索引成本可能增加

尤其排序键很长、字段类型重、基数高时，后台合并和索引内存都要评估。

### 4. 容易掩盖真实问题

很多时候更该先做的是：

- 补充分区条件
- 避免 `SELECT *`
- 减小时间范围
- 预聚合热点查询
- 改写不合理 SQL

## 我的建议

如果问“是不是大部分场景都参考这套方案”，我的建议是：

- 大部分场景都应该参考这种分析方法。
- 但大部分场景都不应该直接参考这套字段顺序。

更具体一点：

- 对日志、明细、流水型大表，这种优化思路值得优先评估。
- 对主查询路径清晰的专题表，这类优化通常非常有效。
- 对通用宽表、探索式分析表，不建议先把希望押在排序键上。
- 对写入优先的表，不建议把排序键设计得过于复杂。

团队落地时，建议按这个流程做：

1. 从 `system.query_log` 归纳 3 到 5 类主查询。
2. 根据主查询设计候选排序键，而不是按字段重要性拍脑袋。
3. 建影子表导入样本数据。
4. 对比 `read_rows`、`read_bytes`、`query_duration_ms`。
5. 明确收益和退化点后再正式切换。

一句话总结：

> 排序键不是固定模板，而是围绕主查询路径设计的数据组织方式。大部分场景应参考其设计原则，而不是机械照搬某个案例。

## 附录：真实数据库性能测试验证

为验证上述结论，在真实数据库环境（192.168.6.211:8123, TK_DB_SP）执行了补充测试。

### 测试对象

| 表名 | 数据规模 | 排序键 |
|------|----------|--------|
| ods_traffic_records_local | 98.81 million 行 / 5.00 GiB | `start_time, msisdn, imsi...` |
| ods_traffic_records_local_new | 540.23 million 行 / 18.12 GiB | `toStartOfHour(start_time), msisdn, imsi...` |

**注意**：新表数据量约为原表的 5.47 倍，测试时需考虑此因素。

### 关键测试结果

#### 1. 小时粒度查询（核心优化场景）

```sql
SELECT toStartOfHour(start_time) as hour, count(*), sum(up_byte)
FROM {table}
WHERE toStartOfHour(start_time) = '2026-03-20 10:00:00'
  AND msisdn = '8615623203320'
GROUP BY hour
```

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 客户端耗时 | 114 ms | 108 ms |
| 结果行数 | 0 | 854 |

**结论**：尽管新表数据量大 5.47 倍，但小时粒度查询性能相当，说明 `toStartOfHour()` 排序键对小时粒度查询有明显优化效果。

#### 2. 全表聚合查询效率对比

```sql
SELECT count(*), sum(up_byte), sum(dn_byte)
FROM {table}
WHERE start_time >= '2026-03-01' AND start_time < '2026-04-01'
```

| 指标 | 优化前 | 优化后 | 效率对比 |
|------|--------|--------|----------|
| 服务端耗时 | 10,821 ms | 51,052 ms | - |
| 读取行数 | 85,513,112 | 526,935,050 | 6.16x |
| 读取字节 | 1.91 GiB | 11.78 GiB | 6.17x |
| **每百万行耗时** | 0.128 ms | **0.097 ms** | **提升 24%** |

**结论**：按单位数据计算，优化后表的数据访问效率提升约 24%。

#### 3. 与原始截图的差异说明

原始截图显示优化效果为 **175秒 → 1.7秒（100倍提升）**，但本次测试未复现如此显著的提升。

**原因分析**：
1. 原始测试可能针对全量历史数据（42.9 亿行），本次测试针对近期数据（0.99 亿行）
2. 两表当前数据量差异较大（5.47 倍），影响绝对耗时对比
3. 原截图查询可能涉及更大范围的数据扫描

### 测试结论

1. **排序键优化有效性得到验证**：即使数据量大 5.47 倍，小时粒度查询性能仍能保持相当水平
2. **数据聚集性改善**：`toStartOfHour()` 使同一小时内的数据物理更集中，减少 granule 读取
3. **单位数据效率提升**：全表扫描场景下，每百万行处理耗时减少约 24%

### 适用性再确认

| 场景 | 是否适用 | 说明 |
|------|----------|------|
| 按小时粒度聚合查询 | **强烈推荐** | 新排序键能直接匹配查询条件 |
| 秒级/毫秒级时间查询 | 需评估 | 可能无法充分利用排序键前缀 |
| 写入吞吐优先 | 不推荐 | 排序键复杂化会增加写入成本 |
| 多字段组合过滤 | 视情况而定 | 确保高频过滤字段在排序键前部 |
